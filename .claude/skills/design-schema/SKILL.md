# 从需求到表设计

**输入**：一句业务需求（"我要管理生产工单"）。
**产出**：一份建表 SQL + 一份生成器配置说明 —— 交给 `/new-module` 直接往下走。

> 这个 skill 是**提问的顺序**，不是知识本身。设计规则全在 `docs/生成器/` 五篇里，
> 每一步都指向对应那篇。**别凭记忆答**，那几篇里记着"做不到什么"和踩过的坑。

---

## 〇、先问清楚（信息不全就别往下）

1. **这个业务对象是什么？** 一句话说清它代表什么现实事物
2. **一次管理一条，还是一批？** —— 决定是普通表还是主子表
3. **它属于哪个模块？** —— 决定前端目录与菜单挂在哪（`biz` 之类）
4. **有别的角色要用吗？** —— 决定菜单是否需要角色授权

---

## 一、定表形态（**先做这一步，它决定后面全部**）

读 `docs/生成器/表与关联.md`。

**生成模式只有三种，且互斥** —— 别想着组合：

| 业务长什么样 | 表形态 |
|---|---|
| 一个对象一张表 | **普通表** |
| "一个主单 + 若干明细行" | **主子表**（一对多） |
| "自己挂自己"（分类树、部门树） | **树表** |

**⚠️ 别把关联都当成生成模式。** 那篇里写清了：
一对多以外的关联（多对一、一对一）是**字段级关联**，不是生成模式；
多对多要另找路子；**枚举不要建关联表**。

**表设计的两条全局约定**也在那篇开头 —— 一定要读到，否则后面全要返工。

---

## 二、定字段与控件

读 `docs/生成器/字段类型.md`。

逐字段过这三个问题：

1. **它是什么** —— 用业务语言说清，这决定了控件与校验
2. **用哪个控件** —— 在那篇的 **17 个 `htmlType`** 里挑
3. **存储用什么类型** —— 那篇每个控件都带存储建议，**照做**

> ⚠️ **那篇还有一节「现在做不到的事」** —— 规划时别指望。
> 常见的坑在这：某些组合根本没有模板分支。

**字段命名**：跟表里已有字段的风格一致。**先看同模块已有的表**再定。

---

## 三、写校验规则

读 `docs/生成器/校验规则.md`。

⚠️ **第一步是看那篇的 §1「规则键的真实覆盖」表** —— 那是全篇最该看的一张表。
**规则键前后端覆盖不一致**，写了只在前端生效的规则，绕过前端就能写脏数据。

规则写成 `validation_rule` 单列 JSON，**那是校验的唯一来源**，前后端都从它派生。

---

## 四、选择类字段的选项从哪来

`select` / `radio` / `checkbox` 有**三种来源，优先级递减**：

| 情况 | 用哪个 |
|---|---|
| 是/否、启用/停用这种**一次性的小枚举** | 写死代码 `{"options":[...]}` |
| 稳定的枚举、**多个模块会用** | **字典**（建字典 + 配 `dict_type`） |
| 部门、设备、物料这种**会变的数据** | 接口 `{"optionsApi":"..."}` |

> ⚠️ **想用写死/接口，必须把 `dict_type` 清空** —— 字典优先级最高，会盖掉它。
> 存储一律 `varchar`（`char(1)` 装不下以后增长的编码值）。
> 细节见 `校验规则.md` §2。

---

## 五、定查询条件

读 `docs/生成器/查询条件常用非常用.md`。

按那篇的原则挑哪些进「常用」：**目标是默认显示的条件恰好占满一行（约 3 个）**，
次要的收进「展开查看更多」。

**这一步由你来规划，不是建表者逐列点。**

---

## 六、补齐惯例列

每张业务表都要有这几个（照同模块已有表的写法）：

```
del_flag      char(1)      comment '删除标志（0存在 2删除）'
create_by     varchar(64)  comment '创建者'
create_time   datetime     comment '创建时间'
update_by     varchar(64)  comment '更新者'
update_time   datetime     comment '更新时间'
remark        varchar(500) comment '备注'
```

---

## 七、产出

### ① 建表 SQL

- 写进 `backend/sql/` 下一个新脚本
- **表和每个字段的 `comment` 必须有** —— 生成器拿它当表单 label、列表列名、搜索提示。
  漏了注释，生成的页面全是英文变量名，得手工返工
- 脚本以 `drop table if exists` 开头（可重复执行）

### ② 生成器配置说明

交给 `/new-module` 用，写成一张对照表：

| 项 | 值 |
|---|---|
| 生成模式 | 普通表 / 主子表 / 树表 |
| `packageName` | 默认已是项目业务包，不用改 |
| `moduleName` | 如 `biz` |
| `businessName` | 如 `workOrder`，决定前端目录名与 API 文件名 |
| `functionName` | 如 `生产工单`，进菜单 |
| `parentMenuId` | 决定生成 SQL 里菜单挂在哪 |
| 查询条件分组 | 哪些常用、哪些折叠 |

## 排查

- **不知道某个字段该用什么控件** → `docs/生成器/字段类型.md`，别猜（有的控件根本没有模板分支）
- **拿不准两条数据什么关系** → `docs/生成器/表与关联.md`，**先确定生成模式再动手**
- **规则写了但不生效** → 查 `校验规则.md` §1 的覆盖表，多半写在了不支持的端
- **表已经建好了才想起设计** → 别改表，先看 `docs/生成器/模板增强清单.md` 的坑，
  再决定是重导还是补配置

## 汇报

```
表：<表名>（<形态：普通表/主子表/树表>）
字段：N 个（控件分布：text 5 / select 2 / date 1 …）
关联：<与谁关联，什么类型；没有就写"无关联">
校验：<写了哪些规则，前后端是否都覆盖>
选项来源：<字典 N 个 / 写死 N 个 / 接口 N 个>
查询条件：常用 N 个（<列出来>），折叠 M 个
产出：建表 SQL → backend/sql/<脚本>；生成器配置 → 见上表
拿不准的：<直说>
```

**没做的事就不要写成做了。** 拿不准的设计直说，别编一个看起来合理的。
