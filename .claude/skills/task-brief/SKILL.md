# 开工前对齐

> **这个项目衡量 AI 工程化的标准只有一条**：
> *新开一个会话，只给一个任务，AI 能不能**不问人**就把事办对。*
>
> 这条标准**一半取决于 AI，另一半取决于你怎么交代**。这个 skill 管后一半。

## 为什么值得专门做一次

**"帮我加个导出功能"** 和 **"给生产工单列表加按日期区间导出，走已有的导出接口风格，
不要动列表页的查询条件"** —— 后者 AI 一次能做对，前者要来回三轮。

**来回三轮的成本远高于花两分钟写清楚。** 而且来回的过程中 AI 已经改了东西，
你还得先弄清它改了什么。

## 开工前五件事

写不出来就别开工 —— 那说明需求还没想清楚，交给 AI 只会更快地跑偏。

### ① 要什么（说结果，不说步骤）

- ✅ "列表页加一个按日期区间导出的按钮，导出当前筛选结果"
- ❌ "改一下 index.vue 的工具栏，加个 el-button，然后写个 export 方法……"

**怎么做是这个项目的 skill 的事** —— 你说步骤反而会跟 `new-module` / `backend-code`
里已经定好的做法打架。**说清楚要什么结果就行。**

### ② 给哪些上下文

**先判一句话：这件事有没有对应的 skill？** 有就直接用触发词喊它 ——
skill 里已经带着该读的文档、该走的步骤、该避的坑。

| 这件事 | 喊谁 |
|---|---|
| 加业务模块 | `/design-schema` → `/new-module` |
| 手写接口 / Service | `/backend-code` |
| 前端组件 | `/frontend-component` |
| 查库 / 改表 | `/db-manage` |
| 起不来 / 不好使 | `/troubleshoot` |
| 验证模块 | `/verify-module` |
| 打包交付 | `/release` |

**喊了 skill 就不用再交代步骤** —— 那是它的职责。你只需要说清业务意图。

**没有对应 skill 时**，说清**改哪个模块 / 哪个页面 / 哪张表**，
以及**有没有相关的 `docs/` 文档**。

### ③ 怎么算做完（验收标准）

**这一条最常被漏，也最能省时间。** AI 说"做完了"时你拿什么判断？

- "列表能按日期筛出结果" —— 可验证
- "导出按钮点了能下文件，且内容与当前筛选一致" —— 可验证
- "优化一下导出" —— **不可验证，等于没说**

> 能被 `verify-module` 那八项清单覆盖的，直接说"跑一遍 `/verify-module`"。

### ④ 不要做什么（边界）

**AI 最容易"顺手"的地方，正是你不想让它动的地方。**

- "别动列表页现有的查询条件"
- "别改表结构"
- "别引新的依赖"
- "这个模块的代码是生成的，别手改生成物"

**没有边界时，AI 会按"看起来更合理"去改** —— 而那往往不是你想要的。

### ⑤ 一次会话做得完吗

**做不完就拆。** 拆法：按**可独立验证**的块，不是按文件。

- ✅ "先加后端接口并验证" → "再做前端按钮"
- ❌ "先把后端那几个文件改了" → "再改前端那几个"

## 什么时候该开新会话

上下文是会被**污染**的。出现这些征兆就开新的：

| 征兆 | 为什么 |
|---|---|
| 这事跟上个任务**没有共同文件** | 无关上下文纯占位置，还容易让 AI 拿旧结论套新问题 |
| AI 开始**重复问**已经说过的事 | 上下文被压缩过，早期信息丢了 |
| 你**换了个方向**，而旧方向的探索还在上下文里 | AI 会把"我们已经排除的方案"再提一遍 |
| 任务**超过一轮"交出去—等—验"** | 该拆了，不是该开新会话 |

**开新会话时给什么**：只给 ①③④ 三样（要什么 / 验收标准 / 边界）+ 让 AI 自己读
`CLAUDE.md` 和对应的 `docs/`。**不用复述项目背景** —— 那是 `docs/` 的事，复述会失真。

> 这正是 `CLAUDE.md` + `docs/` 分层的意义：**新会话不用人喂背景**。

## 验证：怎么判断 AI 说"做完了"是真的

**这个项目的 AI 都被要求在汇报里写"没做的事"** —— 看到汇报时：

1. **先看"没做的"那一栏** —— 空着或写"无"才继续看别的
2. **要求它给出可验证的证据**，不是"看起来没问题"：
   - 接口通了 → 要请求与响应
   - 页面能用 → 要它自己点过、或跑了 `/verify-module`
   - 文档更新了 → 要它跑过 `doc-scan --check`
3. **跑一遍门禁**（`README.md` 的"提交前跑一遍"）—— **别信"我改好了"，信 exit code**

## 反模式

- **"你先做着，我看看"** —— AI 会按它的理解做一大堆，你再说"不是这样"，来回成本最高
- **一次给五个不相关的需求** —— 上下文互相干扰，且出问题时不好定位是哪件事引起的
- **把验收标准留给"做完再说"** —— 那你只能凭感觉验收，或者全盘重来
- **口头描述改了哪个文件** —— 说业务对象（"生产工单那个模块"），让 AI 自己去找文件

## 汇报

把这个 skill 的产出按下面结构给 AI（**这本身就是一份合格的交代**）：

```
要什么：<一句业务语言的结果>
上下文：<喊哪个 skill / 哪个模块 / 哪张表；没有对应 skill 时说清在哪>
验收标准：<怎么算做完 —— 可验证的说法>
边界：<不要动什么>
拆分：<一次做完 / 拆成哪几块>
```

**写不出这五行就别开工。** 缺哪一行，AI 就会在哪一行上自己发挥 —— 而它发挥的方向未必是你要的。
