# 排查问题

## ⚠️ 铁律：先收集证据，别先猜

**"可能是 X 的问题，我改改看"是最贵的排查方式** —— 改错一处会引入新问题，
而且原来的问题还在。正确顺序是：**定位到层 → 再动手**。

**动手改之前先跑一遍下面三条**，它们能把范围缩到一层之内。

## 一、三条命令定位到哪一层

```bash
# ① 三层连通性 —— 一眼看出断在哪
curl -s -o /dev/null -w "后端:     %{http_code}\n" http://localhost:<后端端口>/captchaImage
curl -s -o /dev/null -w "前端:     %{http_code}\n" http://localhost:<前端端口>/
curl -s -o /dev/null -w "前后端联通: %{http_code}\n" http://localhost:<前端端口>/dev-api/captchaImage

# ② 端口谁占着 —— 注意别连到别的项目
netstat -ano | grep LISTENING | grep -E ':(<前端端口>|<后端端口>)\s'

# ③ 后端日志尾部
tail -50 <后端日志>
```

**读法**：

| 后端 | 前端 | 代理 | 结论 |
|---|---|---|---|
| ✓ | ✗ | — | 前端没起来 |
| ✓ | ✓ | ✗ | **Vite 代理配置**或后端路径不对 |
| ✗ | ✓ | ✗ | 后端没起来 |
| 全 ✗ | | | 中间件没起来，或端口全错 |

> ⚠️ **后端 200 不代表是你连的那个后端。** 开发机上常有别的项目占着 8080 ——
> 症状是**所有路径都 404**。先看 `netstat` 的 PID 是不是你起的进程。

## 二、按层深挖

### 后端起不来 / 起来了但报错

```bash
tail -100 <后端日志> | grep -E "ERROR|Caused by|APPLICATION FAILED"
```

- `Communications link failure` / `Access denied` → **数据库**（下一节）
- `Table 'xxx.yyy' doesn't exist` → **SQL 没导全**，见 `docs/基建/数据库.md`
- `Port already in use` → 端口被占，`netstat` 找 PID
- 启动成功但接口 404 → **路径或权限**，不是启动问题

### 数据库

```bash
# 先确认连的是哪个库（端口错会静默连到别人的）
node scripts/db-query.mjs "select database(), @@port"
node scripts/db-query.mjs "show tables like 'sys_%'"
```

**"表不存在"最常见的原因是 SQL 没导完**，不是表真丢了。
导 SQL 时**逐条看输出**，别用 `| head` 把错误过滤掉 ——
MySQL 客户端**遇错即停**，报错行之后的内容全部没执行（实测踩过，见 `AI工程化需求.txt` §3.23）。

### 前端

- **页面空白 + 控制台报错** → 看控制台的第一个 error，通常是 import 路径或类型没导出
- **`Cannot read property of undefined`** → 多半是 `src/types/api/index.ts` 的 barrel 没合并
- **点了没反应** → 看网络面板，多半是接口 4xx（权限）或 5xx
- **样式看着像 bug** → **先全量刷新**！Vite HMR 会留中间态，见 `docs/基建/像素回归测试.md`
- **前端起来了但端口不对** → Windows 上 80 被占会**静默换到 81**

### 权限类

**"按钮不显示"和"按钮点了 403"是两种不同的病**：

- 不显示 → `sys_menu` 里缺那条 `F` 记录（或 `perms` 拼错）
- 403 → 两处都有但**串不一致**（`@PreAuthorize` vs `sys_menu.perms`）

**改完权限必须重新登录** —— 菜单和权限缓存在 Redis 里。
详见 `docs/基建/框架分层与权限约定.md`。

## 三、症状 → 文档

**`docs/README.md` 末尾有一张「症状 → 文档」索引**，按**现象**找比按类型翻快。
拿你那句话里的关键词去那张表对一下 —— 大部分坑都已经记在那儿了，并且写了为什么。

**先查那张表再动手。** 它是这个项目踩过的坑的集合。

## 四、改完之后

1. **确认问题真的没了** —— 不是"看起来好了"，是复现步骤走一遍不出现
2. **跑门禁**：`node scripts/typecheck.mjs` + `node scripts/lint-ratchet.mjs`
3. **把新踩的坑记下来** —— 就近写进对应 `docs/` 的 `## ⚠️ 坑`。
   不记的话，下一个人（或下个月的你）会再踩一次

## 排查

- **不知道去哪查** → `docs/README.md` 的症状索引
- **三条连通性全 200 但功能不对** → 不是连通性问题，是**业务逻辑或数据**问题
- **改了没生效** → 后端要 `mvn install` 再重启；生成器模板 `vm/` 同理；
  权限要重新登录
- **`db-query` 拒绝了你的语句** → 它只放行只读查询。写操作走 `db-manage`

## 汇报

```
现象：<用户说的原话>
定位：<哪一层出的问题，怎么定的>
根因：<为什么>
处理：<改了什么>
验证：<复现步骤走一遍，确认没了 —— 没验证的明说>
新坑：<写进哪份文档了；没有就写"无">
```

**没能定位就直说没能定位**，并给出已经排除的可能。
**"我改了但不确定好没好"比"我猜是 X 然后改了"诚实得多，也有用得多。**
