AI 工程化配置需求与实施状态
================================================================

> 这份文档记录：本项目要做成什么样的「AI 友好工程」，以及**每一项的当前状态**。
>
> 状态标记：✅ 已实现 · 🟡 部分实现 · ⬜ 待办
>
> 用途有二：
>  1. 给 AI 看的「这个项目已经有哪些约定和工具」——避免重复造轮子
>  2. 给自己看的「还差什么」——待办项就是后续的排期来源
>
> 与 `CLAUDE.md` 的分工：`CLAUDE.md` 是**每次会话自动加载**的索引与铁律，
> 只留最高频的东西；本文是**完整的需求台账**，不自动加载，需要时来查。


一、目标
----------------------------------------------------------------

让 AI 能在这个工程里**独立、正确地干活**，而不是每次都要人从头解释。

具体拆成四件事：

1. **知道有什么** —— 项目有哪些模块、每个模块横跨哪些文件、改哪里会影响哪里
2. **知道为什么** —— 为什么这么做、哪些看着像 bug 其实不是（防止AI"好心"改坏）
3. **有工具可用** —— 验证手段（类型检查、像素回归）、操作手段（生成器、模板实例化）
4. **知道怎么改文档** —— 改动如何沉淀回知识库，避免文档比代码先过期

> 核心判断标准：**新开一个会话，只给一个任务，AI 能不能不问人就把事办对。**
> 做不到的地方，就是需求缺口。

三、已实现的 AI 工程化能力
----------------------------------------------------------------

### 3.1 知识分层：CLAUDE.md + docs/ ✅

**问题**：起初所有知识挤在一个 `CLAUDE.md`（28KB）里，每次会话全量加载，
不管这次任务是改主题还是加模块，都要先吞下全部。

**做法**：拆成两层——`CLAUDE.md` 只留**索引 + 铁律**（5KB），正文进 `docs/`。

| 文件 | 内容 |
|---|---|
| `CLAUDE.md` | 文档入口、7 条铁律、仓库结构、启动、端口、数据库（约 5KB，自动加载） |
| `docs/README.md` | 总目录。三段：**按任务找** / 按类型列 / **症状 → 文档** |
| `docs/基建/` | 环境与启动、框架分层与权限约定、主题系统、类型检查棘轮、像素回归测试、数据库 |
| `docs/生成器/` | 字段类型、校验规则、表与关联、模板增强清单、查询条件常用非常用 |
| `docs/业务/` | 一个业务模块一份（4 份演示模块 + 总览） |

设计要点：

- **索引每行必须带「什么时候读」**，不只写标题——读的人才能判断要不要读
- 分类只有三类，判断标准是「**改了它会不会只影响一个业务模块**」
- **不单开「决策」和「已知坑」目录**：决策离开所属机制就没人读，
  改为每份文档自带 `## 设计取舍` / `## ⚠️ 坑`
- `docs/README.md` 带一份**症状索引**（"菜单不显示→哪篇"），排查时比按类型翻快

### 3.2 业务模块文档自动生成 ✅

**问题**：一个模块的事实散落在 6 处（表注释、生成器配置、菜单权限、字典、
代码落点、SQL 脚本），手抄必错、改一次过期一次。

**做法**：`scripts/doc-scan.mjs` 从数据库 + 代码目录抽事实，
只覆写文档里的 `<!-- BEGIN GENERATED -->` 标记块，**块外的叙述一字不动**。

- 人在叙述里写脚本抽不出来的：`业务规则` / `设计取舍` / `⚠️ 坑`
- `--check` 只读体检：缺文档 / 生成块过期则 exit 1，可挂 CI
- 能识别「有表但没挂菜单」（测试遗留）和「主子表的子表」（折叠进主表）

### 3.3 可执行的技能：.claude/skills/ ✅

| skill | 触发场景 | 内容 |
|---|---|---|
| `new-module` | 「加一个模块」 | 建表 → 生成器 → 落地文件 → 菜单 SQL → 重启验证，含排查清单 |
| `start-project` | 「启动/重启」 | 中间件 → 后端 → 前端 → 全链路验证 → 端口占用排查 |
| `update-docs` | 「更新文档」 | **「改了什么 → 更新哪份文档」路由表** + 三条硬约束 |

> `update-docs` 的路由表是这套体系的关键：没有它，改动不会沉淀回文档，
> 文档就开始过期——而过期的文档比没有文档更糟。

### 3.5 代码生成器的 AI 适配 ✅

代码生成器是上游框架就有的，但**生成物对本项目不够用**，做了这些改造：

| 改造 | 说明 |
|---|---|
| **17 种控件** | 原版只有 11 种且 `datetime` 名不副实；补了 `date`/`time`/`number`/`switch`/`month`/`year`/`rate`/`treeselect`，并把格式类（手机号/邮箱）改用 `pattern` 规则而非新控件。**准确清单见 `docs/生成器/字段类型.md` §1** |
| **`validation_rule` 单列 JSON** | 校验规则的**唯一来源**，前后端都从它派生。补上了原版**完全缺失**的服务端校验（原版生成的 CRUD 服务端零校验，绕过前端就能写脏数据） |
| **`is_common` 查询条件分组** | 常用直接显示、非常用折叠；附 AI 的**规划原则**（按业务重要性分，目标占满一行） |
| **两个 v3ts 模板功能对齐** | 普通表与树表是两套独立模板，改一处必须改另一处（踩过两次） |
| **表单/查询区兜底分支** | 未匹配的 `htmlType` 退化成文本框，不再**静默丢字段** |

> 记录在 `docs/生成器/` 三篇里，含踩过的坑（字段静默消失的三种成因、Velocity 的两个陷阱）。

### 3.6 质量门禁 ✅

**项目没有单元测试**（原版也没有），改为**四道**针对性的门禁：

- **类型检查棘轮** —— 存量 436 个错误记进基线，只对**新增**失败。
  为什么不修完再上：修完要动 30+ 文件，而在此之前**没有任何手段能发现"这次改动引入了新错误"**
- **ESLint 棘轮**（见 §3.16）—— 存量 728 个问题记进基线，同样只报新增
- **像素回归** —— 改 `app-main`/主题/布局后必跑。`--tolerance 2` 是按实测校准的
  （严格 0 下同页面两次采集差 19 像素，`maxDelta=2/255`，是抗锯齿抖振
- **文档一致性** —— `doc-scan.mjs --check`，见 §3.2

### 3.7 模板化机制 ✅

**问题**：仓库要能当模板复用，但不能靠"用的时候全局搜索替换"——漏一处就编译不过。

**做法**：`@@KEY@@` 占位符，定义在 `scripts/init.config.mjs`（单一事实来源）。

- 13 个变量：项目名、slug、Java 包根、Maven 模块前缀、启动类名、库名、密码、4 个端口……
- **同时作用于文件内容和文件/目录名** —— 所以模板态下会有
  `backend/@@MAVEN_ARTIFACT_PREFIX@@-admin/src/main/java/@@JAVA_PACKAGE_ROOT@@/@@APP_CLASS@@.java`
- `init.mjs` 两阶段执行：先改名字（深的先改，父路径才还有效），再改内容
- `@@JAVA_PACKAGE_ROOT@@` 是唯一会**展开**的变量（`com.example` → `com/example/` 目录层级）
- 实例化后写 `.template-init.json` 记录本次用的值（已在 `.gitignore` 里）

### 3.10 减少打断：.claude/settings.json ✅

高频**只读**命令加进 `permissions.allow`，不必每次确认：

```
node scripts/doc-scan.mjs *        # 文档生成与体检
node scripts/typecheck.mjs *       # 类型棘轮
node scripts/init.mjs --check *    # 模板体检（只读）
node scripts/templatize.mjs --dry-run *
netstat *
```

⚠️ **`docker exec` 一律保持询问**，虽然查库很高频。
原因：权限规则是**前缀匹配**，一条 `Bash(docker exec *)` 会连
`... mysql -e "DROP TABLE ..."` 一起放行 —— 没有既方便又安全的写法。

✅ **已根治（见 §3.15）**：不是放宽权限，而是造一个**只读的封装** `scripts/db-query.mjs`，
然后放行**那个封装**。高频只读查询走它（不再打断），其余 `docker exec` 用途（导 SQL 等）仍然询问。

### 3.11 编辑器与行尾：.editorconfig ✅

本仓库行尾原本是**混杂**的（`.gitattributes` 里专门记过这件事：
`git diff` 常年被纯行尾噪音淹没，「真实改动再也看不出来」）。

`.editorconfig` 规定 `end_of_line = lf` 来**逐步收敛**：

- 它只在**保存**某个文件时生效 —— 是「编辑到哪个文件、哪个文件才归正」
- **不是**一次性重写 25000 个文件（那正是 `.gitattributes` 拒绝做的事）

例外：`.bat` / `.cmd` 强制 CRLF（Windows 批处理认这个）；
`backend/bin/{clean,package}.bat` 是 GBK 编码，`charset = unset` 不动它们。

### 3.12 专用子代理：.claude/agents/ ✅

两个任务足够长、足够独立，适合丢给子代理跑完再回主线，不占用主上下文：

| 代理 | 干什么 |
|---|---|
| `page-generator` | 从建表 SQL 到落地页面的一条龙：建表 → 生成器 → 落地文件 → 菜单 SQL → 重新打包 → 文档骨架 → **逐项验证** |
| `style-regression` | 改样式后的完整回归：采图 → 逐像素比对 → `--grid` 定位差异落在哪一块 → 判定 |

两个代理都**先读 `docs/` 里的对应文档再动手**，且汇报格式里要求
**「没做的事不要写成做了」** —— 这类代理最容易出的问题是把"我以为会成功"写成"已完成"。

### 3.13 文件存储可切换：本地磁盘 / MinIO ✅

**问题**：上传只有一种去处——本地磁盘（`ruoyi.profile` 指向的 `uploadPath/`）。

**难点不在「再加一种上传」**：现状是一条隐式约定串起来的 ——
上传返回相对路径 → 数据库存相对路径 → 前端渲染时拼 `VITE_APP_BASE_API` →
`/profile/**` 由 Spring 映射到本地磁盘。前端有 5 处拼 URL 的逻辑，其中
`FileUpload` / 富文本 `Editor` / 用户头像这 3 处**没有 `isExternal` 兜底**；
而预签名 URL 会过期，**根本不能存进数据库**。

**做法**：对外 URL 形状**始终是 `/profile/...`**，MinIO 模式下由后端代理读取。
于是**前端零改动、数据库零改动**，`SecurityConfig` 的匿名放行与 `RefererFilter`
防盗链天然继承。（`vite.config.ts` 本来只代理 `/dev-api`，所以 `/profile/**` 的流量
本来就全部经过后端 —— 这不是新增一跳，是换了那一跳干的事。）

- 接口 `FileStorageService` + 本地实现放 `@@MAVEN_ARTIFACT_PREFIX@@-common`；
  **MinIO 实现单独一个模块**，不需要的项目删一行 dependency 即可，SDK 永不下载
- **对象键 = 相对路径去掉 `/profile` 前缀**，映射收口在 `FileStoragePath` 一处，
  两种实现共用 —— 顺带修掉原实现里那个会产生 `/profile//upload`（双斜杠）的 bug
- **存量本地文件回退**（`fallback-local`）：读/删在对象不存在时委派给本地；
  **写永远进 MinIO**，否则新旧数据持续分叉
- 顺带补上**服务端上传校验**（白名单 + 大小上限），两个实现共用同一道，绕不过去
- MinIO 进 `docker-compose.yml`；桶由一次性容器 `minio-init` 建 ——
  后端不持有管理凭据，且 MinIO 抖动不会阻断后台启动
- 两种模式**都做了端到端验证**（含存量回退、删除、匿名放行、失败路径）

详见 `docs/基建/文件存储.md`。

### 3.14 选择类字段的三种选项来源 ✅

**问题**：`select` / `radio` / `checkbox` 的选项**只能来自字典**。想要一组简单的
「是/否」「启用/停用」也得先建字典再配 `dictType`；而部门、设备、物料这类**会变的数据**
本来就该从接口取。

**做法**：选项来源扩成三种，**优先级递减**，都配在既有的 `validation_rule` JSON 里
（**不动 DDL** —— `FieldRule` 忽略未知键，实测确认）：

1. **字典** —— `gen_table_column.dict_type`（现状）
2. **写死代码** —— `{"options":[{"label":"启用","value":"1"}]}`
3. **接口** —— `{"optionsApi":"/x/list","optionLabel":"name","optionValue":"id"}`

- 新增前端组合式函数 `useApiOptions`（走既有的 `@/utils/request`，自动导入）
- 列表列**三种来源共用 `<dict-tag>`** —— 它本就接受任意 `{label,value}` 数组，不用改组件
- 顺带清掉两处**不可达的死分支**（`&& $dictType`，被前一分支抢先命中）
- **两套模板 × 三个区块（+ 子表）共 6 处**都改了，并逐个验过产物

**顺带纠正的存储建议**：`select`/`radio`/`checkbox` 的存储从 `char(1)` 改为 **`varchar`** ——
`char(1)` 装不下以后增长的编码值（`PENDING`）或超过 9 个的选项，升级要改表。
`switch` 例外保留 `char(1)`：它的 `'1'`/`'0'` 是模板里硬编码的代码契约，永远两值。

详见 `docs/生成器/字段类型.md` §1 与 §3。

### 3.15 技能体系的自洽性保障 ✅

**问题**：skill 失效是**静默的** —— 路径写错、frontmatter 字段拼错，
都不会立刻报错，只会在某天用到时把人带沟里。而 skill 里全是路径引用。

**做法**：规范 + 体检器 + 一个安全封装，三件配套。

| 产物 | 说明 |
|---|---|
| `docs/基建/技能规范.md` | 写 skill 的规则。**官方硬约束**取自 Anthropic 的 `quick_validate.py`（6 个允许字段、name kebab ≤64、description 无尖括号 ≤1024）；**项目约定**是触发词 / ≤200 行 / 引用路径存在 / 有排查小节 |
| `scripts/skill-lint.mjs` | 体检器。**硬约束违规 exit 1，项目约定只警告** —— 代价不对称，处理方式就不对称 |
| `scripts/db-query.mjs` | 只读查库封装（见 §3.10）。**用能力换权限**：放行这个脚本，`docker exec` 仍然询问 |

**三个关键设计**：

- **行数上限 200，比 `docs/` 的 400 更严** —— 文档是按需读的，skill 是**每次被完整读入上下文**的
- **默认跳过 `el-*` / `element-plus-*`** —— 那 39 个是引用技能（§4.3），
  它们**不该满足本项目约定**：改了就说不清是上游内容还是本地改动，下次 `--fetch` 还会覆盖
- **路径检查只认仓库根相对的** —— skill 里反引号包的东西五花八门（JSON 片段、shell 参数、
  npm 包名、示意性简写），全当路径查会淹在误报里，真正该查的反而看不见。
  顶层目录**从磁盘现读**，不硬编码

**已验证**：`skill-lint` 自测能抓到 3 个硬约束 + 2 个约定（含「目录名与 name 不一致」）；
`db-query` 自测挡住 7 类危险输入，含 `select 1; drop table x`（多语句）
与 `/*x*/delete`（注释藏写操作）。

**顺带修的**：`db-query` 最初按「以 `-` 开头就跳过」解析参数，
结果以 `--` 注释开头的 SQL 被整个当选项吞掉、静默变成「没给 SQL」。
改为只跳过**已知选项名**。

### 3.16 前端代码规范：ESLint 棘轮 + Prettier 渐进收敛 ✅

**问题**：前端此前**完全没有 lint**（无 ESLint / Prettier / stylelint），
所以"前端代码规范"这件事一直没着落 —— 而它本该由工具强制，不是写给人看。

**做法**：机械能判的交给 ESLint（棘轮），**Prettier 只管格式且不参与棘轮**。

| 产物 | 说明 |
|---|---|
| `frontend/eslint.config.js` | 扁平配置。只取 `flat/essential` + `vueTsConfigs.recommended` 两个**正确性**档位 |
| `scripts/lint-ratchet.mjs` | ESLint 棘轮，同 `typecheck.mjs` 的模式。存量 **728** 个问题 |
| `frontend/.prettierrc.json` + `.prettierignore` | 风格取值**与现有代码实测对齐**（单引号、无分号、2 空格、LF） |

**⭐ 关键取舍一：Prettier 不能棘轮，所以按 `.editorconfig` 那套「渐进收敛」办**

Prettier 没有"只格式化新代码"模式 —— 跑一次就是**全量重写 197 个文件**。
那不是棘轮，是一次性大 diff。所以只配不跑，靠编辑器保存时归正
（与 `.editorconfig` 治行尾的思路一致，连理由都一样）。

**⭐ 关键取舍二：只取"正确性"档位，不取风格**

不加 `stylistic`（那是 Prettier 的活，而且格式类问题数量巨大无信息量，会撑爆基线），
不加 `strict`/`strictTypeChecked`（在 436 个存量类型错误之上再加噪音）。
判断标准：**违反了会出真 bug 就收，只是"看着不统一"就不收**。

**⚠️ 关键取舍三：`vite.config.ts` 被排除**

它含**表达式位置**的模板占位符（`port: @@FRONTEND_PORT@@`）—— 模板态下不是合法 TS。
**同一个文件在模板态与实例态报出的东西不一样**，而棘轮基线必须在两种状态都成立，
否则每次切状态都是假漂移。它的正确性由 `vite build` 兜底。
（另外 3 个含占位符的前端文件占位符在**字符串里**，解析正常，不用排除。）

> 顺带印证了一件事：模板态下 `typecheck.mjs` 现在**本身就是坏的** ——
> `vite.config.ts` 的占位符让 vue-tsc 中止，只报 1 个错误而非 436 个，
> 所以那份 436 的基线是**在实例态录的**。它的告警逻辑正确地拒绝了 `--update`。

**已验证**：棘轮正向（无新增 → exit 0）与反向（引入 `any` → 报出并 exit 1）均通过。

**用法**：

```bash
node scripts/lint-ratchet.mjs            # 比对基线，有新增则 exit 1
node scripts/lint-ratchet.mjs --update   # 写为新基线
node scripts/lint-ratchet.mjs --list     # 列出全部问题
```

详见 `docs/基建/前端代码规范.md`。

### 3.21 ⚠️ 严重：同机多实例会互相删掉对方的容器 ✅ 已修

**2026-09-15 实测时真出的事故**：在新实例目录里跑 `docker compose up -d`，
**把同机上另一个实例（`mes`）和 `demo` 实例的容器删掉了**
（`mes` 实例的 MySQL / Redis，以及 `demo` 实例的 MinIO 容器）。**数据没丢**（卷还在），但那些项目被搞停了。

**根因：`deploy/docker-compose.yml` 没有 `name:`。**

compose 的项目名默认取 compose 文件所在**目录名** —— 而**每个实例的 compose 都在
`<项目>/deploy/` 下**，所以**所有实例的项目名都叫 `deploy`**。
更巧的是**服务名也一样**（都是 `mysql` / `redis` / `minio`）。

于是新实例 `up` 时，compose 认为「项目 `deploy` 的服务 `mysql` 还是那一个，
只是配置变了」→ **把旧容器替换掉**。一个实例启动，另一个实例就没了。

**为什么数据没丢**：卷名是**带前缀声明**的（`@@PROJECT_SLUG@@-mysql-data`），
两个实例的卷名不同，所以只是容器被替换，卷各归各的。**纯属侥幸** ——
文件头原本只警告了「共用卷名会共用数据库」这一条，**漏了项目名这条独立的轴**。

**修法**：在 compose 文件顶层加 `name: @@PROJECT_SLUG@@`，
并把文件头的警告补成**两条隔离边界**（项目名 + 卷名），说明为什么缺一不可。

> ⚠️ **已有数据的实例不能直接套这个修法** —— 改 `name:` 会连带换掉卷名前缀
> （`<项目名>_<卷名>`），实例会认不出原来的卷、看起来像"数据没了"。
> 老实例要么保持原样，要么**先把卷改名**（`docker volume create` + 拷贝 + 确认 + 删旧）。
> 这一点也写进了 compose 文件头的警告。

**顺带修正了一个认知**：文件头原来暗示"改卷名就隔离了"，
实际**项目名是更隐蔽的那条**——因为它不写在文件里，是目录名推导出来的。

### 3.23 ⚠️ 阻断级：基线种子 SQL 的 INSERT 顺序错误 ✅ 已修

**症状**：全新实例导 `backend/sql/ry_20260417.sql` 时报
`ERROR 1146: Table 'xxx.sys_notice' doesn't exist`（第 555 行）。

**根因**：两条 `insert into sys_notice` 被**错放在第 13 节「参数配置表」里**，
而 `sys_notice` 的 `create table` 在**第 17 节**（第 625 行）——
**先插后建**。第 17 节那个「初始化-公告信息表数据」小节标题还在，**内容是空的**，
说明是当初编辑时数据错位飘上去的。

**后果**：MySQL 客户端**遇错即停**，第 557 行之后的**全部没执行**。
实测缺了 **7 张表**：

```
sys_logininfor / sys_job / sys_job_log / sys_notice / sys_notice_read
gen_table / gen_table_column        ← 代码生成器就靠这两张
```

**`gen_table` 一缺，代码生成器整个废掉** —— 而 `new-module` 正依赖它。
**每次全新环境都会踩，且报错信息（"表不存在"）指向的是错误的方向** ——
看起来像"少了张通知表"，实际是"后面全没跑"。

**修法**：把那两条 INSERT 移回第 17 节的空小节里，并在那里写了注释说明为什么不能上移。

**验证**：重建库导一次 → **无报错、31 张表全在**（修复前 24 张）。

- **映射表硬编码**（`SUB_COMPONENT` / `DESIGN_SPEC`）—— 子组件归并是**语义**关系：

- **`el-row`/`el-col` 是例外**：没有组件技能，只在 `element-plus-design-layout` 里。
  `el-col` 是第二高频标签（279 次），**只拉组件技能会漏掉整块网格布局**
- **服务型组件最容易漏**（`ElMessage` / `ElMessageBox` / `ElNotification` / `ElLoading`）——
  它们是函数调用不是标签
- **不要手工编辑落地的 SKILL.md** —— 下次 `--fetch` 会覆盖，且那样就说不清是上游内容还是本地改动

**版本核对**（项目锁 `element-plus@2.13.1`，技能库只声明 "2.4+" 下限）：
组件级 76/77 命中（唯一不匹配 `el-datetime-picker` —— 2.13.1 已并入 `el-date-picker type="datetime"`，
说明技能库有旧内容残留）；`el-table` 31 个 prop 抽查 100% 命中。
**兜底**：即使某个 API 过时，`typecheck.mjs` 棘轮用**本地类型定义**检查，会直接报错，不会静默。

**⚠️ 网络坑**（拉取时会撞上，记下来省得再查）：

- **`raw.githubusercontent.com` 在部分网络下不通**（实测 Connect Timeout），
  而 `api.github.com`、`codeload.github.com` 通 —— 所以脚本走**打包下载整仓**：
  一次请求约 1 秒完成。逐个抓单文件既慢（40 个串行请求跑不完）又会被墙
- 解压时**不能用 `tar -C <绝对路径>`** —— GNU tar 会把 `C:\...` 里的冒号当成 `host:path` 语法，
  报 `Cannot connect to C`。要在 `cwd` 里用相对路径

五、维护约定
----------------------------------------------------------------

### 5.1 改完代码要更新文档

见 `.claude/skills/update-docs/SKILL.md` 的路由表。三条硬约束：

1. 单份文档超过 400 行必须拆
2. `docs/README.md` 每行必须带「什么时候读」
3. 不新开第 4 个分类

### 5.2 往模板里加东西时

- **别写死项目标识**，用 `@@KEY@@` 占位符（已有变量见 `init.config.mjs`）
- 写完跑 `node scripts/templatize.mjs --dry-run`，看有没有漏网的字面量
- 改了占位符变量本身（增删/改默认值），跑 `node scripts/init.mjs --check` 确认自洽

### 5.3 这份文档本身的维护

实现一项待办后：

1. 把它从「四、待办」移到「三、已实现」，**说清楚做法和为什么**
2. 待办项如果被否决，也别删——写一句「不做，因为……」，
   否则过段时间又会有人重新提出来

### 5.4 本文与 docs/ 的关系

本文是**需求台账**（要什么、做到哪了），`docs/` 是**工程知识**（怎么用、为什么）。
一项需求做完后，**用法与原理进 `docs/`，本文只留一句状态和指针**——
避免同一件事两处维护。
