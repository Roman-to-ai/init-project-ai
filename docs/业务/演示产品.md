## 业务规则

- **8 个字典字段**在列表里渲染成彩色标签（`<dict-tag>`）；其中多值的 `tags` / `scenes`
  线上是**数组**（`@MultiValue` 兜的），组件直接吃 —— **不需要手工 split**。
- **`category_id` 用 `treeselect` 指向自己的分类树**（`/biz/demoCategory/list`）——
  这是**模块间关联**的示例，也是全项目唯一一个「字段依赖另一个模块的数据源」的地方。
- **文件类字段**（`cover_image` / `gallery_images` / `spec_file` / `report_file` / `manual_files`）
  线上也是数组、库里是逗号串；数量/大小/类型约束来自 `validation_rule`，
  但**只在前端生效**（服务端不校验上传数量与格式）。其中：
  - `cover_image`（`{"limit":1}`）是**单图样板** —— 一个相框，上传完在原位回显
  - `gallery_images`（`{"limit":5}`）是**多图样板** —— 可**拖拽排序**，顺序即存储顺序
- **`tag_names` 是多对多的冗余显示列** —— 产品的标签存在辅助表 `biz_demo_product_tag`，
  名称由后端按辅助表重算（逗号分隔），列表 / 导出直接吃它。配法与样板见
  `docs/生成器/表与关联.md` §4。
- **`is_recommend` 是 `tinyint(1)` 存的开关**（全项目唯一一处，其余开关列都是 `char(1)`）：
  表单与响应都是 `true`/`false`（`@FlagValue` 兜的），而**查询区是「是/否」下拉、发 `'1'`/`'0'`**
  —— 那种列的 Java 字段是 `Integer`，且开关本身表达不了「不筛」。见 `docs/生成器/模板增强清单.md`。
- 表单是 **3 列布局**（其余模块都是 1 列），因为字段太多，1 列一屏看不全。

## 设计取舍

- ⚠️ **这是演示模块，不是真实业务表。** 它刻意把 17 种控件铺满，当「生成器能产出什么」
  的活样本。真实业务表**不要**照抄这个宽度 —— 45 个字段里有一半是为了演示控件而加的。
- 跨字段校验挑了「调整金额 < 含税单价」（`adjust_amount` 的 `ltField: unitPrice`）
  **是为了演示机制而选的**，没有真实业务含义。
- `contact_phone` / `contact_email` 用 `input` + `pattern` 规则而非独立控件 ——
  这是本项目刻意推翻的一个决定，理由见
  `docs/生成器/校验规则.md` §5（唯一被推翻的决定）。

## ⚠️ 坑

- **本模块没有特有的坑。** 它暴露出来的问题全是生成器通用的，已收进
