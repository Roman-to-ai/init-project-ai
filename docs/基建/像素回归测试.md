# 像素回归测试

> 项目**没有单元测试**，靠截图逐像素比对。
> **改 `app-main`、主题、布局样式后必须走这一轮** —— 这些改动的影响面是全站的，
> 看不出问题不等于没问题。

## 流程

```bash
# 1. 采基线（7 个路由 × default/dark 两套主题，共 14 张）
node scripts/shot.mjs --out shots/before

# 2. 改代码。改完【全量刷新】再采 —— HMR 会留中间态（见下方「坑」）

# 3. 采改造后
node scripts/shot.mjs --out shots/after

# 4. 逐像素比对 —— 注意 --tolerance 2
python scripts/imgdiff.py shots/before/default-index.png shots/after/default-index.png --tolerance 2
```

**判定标准**：默认主题 0 差异，暗色同。

暗色顶栏图标区有个**已知缺陷**，用 `--mask` **显式排除**，
不要靠嘴说「除某区域外」：

```bash
python scripts/imgdiff.py shots/before/dark-index.png shots/after/dark-index.png \
    --tolerance 2 --mask 1080,0,240,60
```

## 为什么是 `--tolerance 2` 而不是严格 0

实测：严格 0 下同一页面两次采集会有 **19 像素**差（`maxDelta` 仅 **2/255**）——
树形面板边缘的**抗锯齿亚像素抖振**，肉眼不可见。

`--tolerance` 按**单通道色差**容错，只放过这种噪音；而真实的主题差异是
`maxDelta=255`、上百万像素，**低两个数量级，照样抓得住**。

> ⚠️ **用 `--tolerance` 而不是放大 `--max-diff-pixels`** —— 后者会把
> 「19 个像素挪了位」和「19 个像素颜色差 2」一视同仁地放过。

校准结果：`--tolerance 2` 下 **14/14 张两次采集完全一致**（0 像素差异）。

## 哪些路由不能用来做回归

`shot.mjs` 默认集**刻意不含** `/monitor/online`：它的表格行数 = 当前在线会话数，
而脚本每跑一次就登录一次、往 `sys_user_online` 插一条，
**第二轮必然比第一轮多一行**（分页的「共 N 条」也跟着变）。

这是**采集行为本身在改动被采集的数据**，不是渲染问题，隐藏元素也救不了。

`/monitor/operlog` 同理（每次登录都留操作日志）。

> 手动加进 `--routes` 时脚本会警告。

登录页的**验证码图每次请求都变**，脚本已用 `--hide` 默认藏掉 `.login-code-img`
（用 `visibility:hidden` 保留占位，布局不位移）。

新页面若有类似易变元素，用 `--hide <选择器>` 追加。

## `imgdiff.py` 的退出码

| 码 | 含义 |
|---|---|
| `0` | 在阈值内 |
| `1` | 超出阈值 |
| `2` | 用法或 IO 错误 |

定位「差异落在页面哪一块」加 `--grid 8`。

## 依赖

`shot.mjs` 需要 playwright，**装在 `frontend`**（`node_modules` 解析由脚本自己指向）：

```bash
pnpm -C frontend add -D playwright
pnpm -C frontend exec playwright install chromium
```

登录用的是**从 Redis 读回验证码答案**的路子（键 `captcha_codes:<uuid>`）——
**只读，不改配置、不动数据库**；需要 docker 中间件在跑。走不通时用 `--token`。

## ⚠️ 坑

### 改样式后必须**全量刷新**验证

Vite HMR 会缓存中间态。分两次编辑同一文件（如先删 import、再改用到它的代码）时，
浏览器可能停在中间那一刻报 `xxx is not defined`，**看着像真 bug**。

**全量刷新后重现才算数。** 采「改造后」截图前也要先全量刷新，否则采到的是中间态。
