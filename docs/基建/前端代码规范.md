# 前端代码规范

> **什么时候读**：跑 `lint-ratchet.mjs`、改 `eslint.config.js`、或加 lint 规则时。
>
> 一句话：**机械能判的交给 ESLint（棘轮），人写不了的才进 `docs/` 或 skill。**

之前前端**完全没有 lint** —— 所以"前端规范"这件事一直没着落。
本文记录它现在落在哪，以及几个不显然的取舍。

---

## 一、ESLint：棘轮，不是全绿门禁

首次接上时有 **728 个存量问题**。存量太大时，"修完再上"等于永远上不了 ——
那正是当初**类型检查**没有采用的策略（见 [`类型检查棘轮.md`](类型检查棘轮.md)）。

所以照抄同一个模式：

```bash
node scripts/lint-ratchet.mjs            # 比对基线，有新增则 exit 1
node scripts/lint-ratchet.mjs --update   # 把当前结果写为新基线
node scripts/lint-ratchet.mjs --list     # 列出当前全部问题
```

（`frontend/package.json` 里也有 `pnpm -C frontend lint` / `lint:update`。）

- **你不能让它变多**（改坏东西立刻被发现）
- **它会随你减少而收紧**（修掉一个就跑 `--update` 让基线降下来）

**key 不带行列号**（`文件 + 规则 + 消息`）—— 带行列号的 key 在改动后会大面积漂移，
于是每次改代码都报一堆假的"新增"。理由与 `typecheck.mjs` 完全相同。

**已知局限**：消息里嵌了标识符的问题会随改名 churn。
判定方法同 typecheck：看新增与修复的数量是否相等且文件名相同，是则 `--update`。

## 二、⭐ 为什么 Prettier 不参与棘轮

这是本方案里最容易搞错的一点。

| | ESLint | Prettier |
|---|---|---|
| 干什么 | **找问题**（可枚举、可计数） | **重排代码**（全有或全无） |
| 能棘轮吗 | ✅ 存量记基线，只报新增 | ❌ **不能** |

Prettier 没有"只格式化新代码"这种模式 —— 跑一次就是**全量重写 197 个文件**。
那不是棘轮，是一次性的大 diff。

所以 Prettier 按**本仓 `.editorconfig` 那套「渐进收敛」**来办
（`.editorconfig` 注释里写得很清楚：*"不是要一次性重写 25000 个文件"*）：

- ✅ **配好了**：`frontend/.prettierrc.json` + `.prettierignore`
- ✅ **编辑器保存时生效** —— 编辑到哪个文件、哪个文件才归正
- ❌ **不批量跑**

**风格取值跟现有代码对齐**（第一次接上时实测的），否则"渐进收敛"会变成"每行都改"：

| 项 | 值 | 依据 |
|---|---|---|
| `singleQuote` | `true` | 实测单引号 321 处 vs 双引号 139 处 |
| `semi` | `false` | 实测无分号 98 处 vs 有分号 1 处 |
| `printWidth` | `120` | Vue 生态常见值 |
| `endOfLine` | `lf` | 与 `.editorconfig` 一致（那是它专门在治的问题） |

## 三、规则档位：只取"正确性"，不取"风格"

```js
pluginVue.configs['flat/essential']   // Vue 必需规则
vueTsConfigs.recommended              // TS 推荐规则
```

**刻意不加**：

- **`stylistic`（格式类）** —— 那是 Prettier 的活。放进 ESLint 只会和 Prettier 打架，
  而且格式类问题**数量巨大且无信息量**，会把基线撑爆
- **`strict` / `strictTypeChecked`** —— 在 436 个存量类型错误之上再加噪音，
  基线会长到没人看

**判断标准**：一条规则如果"违反了会出真 bug"，收；如果只是"看着不统一"，不收。

## 四、⚠️ `vite.config.ts` 被排除，以及为什么

它含**表达式位置**的模板占位符：

```ts
server: {
  port: @@FRONTEND_PORT@@,   // ← 模板态下不是合法 TS
```

后果：模板态 `Parsing error`，实例态正常。**同一个文件在两种状态下报出的东西不一样** ——
而棘轮的基线**必须在两种状态下都成立**，否则每次切状态都是假漂移。

所以 `eslint.config.js` 显式排除了它。它的正确性由 `vite build` 兜底。

> 前端另外 3 个含占位符的文件（`src/settings.ts` 与 2 个 `.vue`）**不用排除** ——
> 它们的占位符都在**字符串里**，解析正常。

## 五、和类型检查的关系

两者是**互补**的，别指望一个替代另一个：

| | 管什么 | 存量 |
|---|---|---|
| `typecheck.mjs` | 类型正确性（vue-tsc） | 436 |
| `lint-ratchet.mjs` | 代码问题 + Vue/TS 规则（eslint） | 728 |

**生成新模块后两个都要 `--update`** —— 生成的 CRUD 页面按框架统一写法产出，
两类问题都会带进来。理由见 `typecheck.mjs` 文件头：那是框架全代码库的统一写法，
不是新引入的坏味道。

---

## 六、⚠️ 改规则会让基线大面积失效

改 `eslint.config.js` 里的规则档位，等于把老问题全部重新分类 ——
棘轮会把它们全报成"新增"。

**改完规则记得跑**：

```bash
node scripts/lint-ratchet.mjs --update
```

并且**在提交信息里说明改了规则**，否则下一个人看到基线总数突变会以为是代码坏了。
