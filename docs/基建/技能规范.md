# 技能规范

> **什么时候读**：新建 / 修改 `.claude/skills/` 下的技能时。
> 体检用 `node scripts/skill-lint.mjs`（只报问题，不改文件）。

规范存在的理由很实际：**skill 失效是静默的**。路径写错、字段拼错、行数失控，
都不会立刻报错 —— 只会在某天用到时把人带沟里。所以规则要写下来，并且能被机器查。

---

## 一、两类技能，规范只管一类

| 类型 | 识别 | 规范 | 例 |
|---|---|---|---|
| **自建** | 目录名不以 `el-` / `element-plus-` 开头 | **全部适用** | `new-module` / `start-project` / `update-docs` |
| **引用** | `el-*` / `element-plus-*` | **只适用官方硬约束** | 39 个 Element Plus 组件技能 |

**为什么区别对待**：引用的那批是从上游 `jiaiyan/element-plus-skills` 拉的（见 `AI工程化需求.txt` §4.3），
它们**不该满足本项目约定** —— 改了就说不清是上游内容还是本地改动，下次 `--fetch` 还会覆盖。
`skill-lint.mjs` 按目录名前缀跳过它们。

---

## 二、官方硬约束（违反 → skill **装不上**）

来自 Anthropic 官方的校验器 `quick_validate.py`（`skill-creator` 插件内）。
**这些是硬性的，不是风格建议。**

| 项 | 约束 |
|---|---|
| 文件 | 必须有 `SKILL.md`，且**内容以 `---` 开头** |
| frontmatter | 必须是合法 YAML 字典，用 `---\n…\n---` 包住 |
| **允许的字段** | 只有 6 个：`name` / `description` / `license` / `allowed-tools` / `metadata` / `compatibility`。**多一个就报错** |
| 必填 | `name`、`description` |
| `name` 格式 | kebab-case：只有小写字母、数字、连字符；不能以连字符开头/结尾；不能有连续连字符 |
| `name` 长度 | ≤ 64 字符 |
| `description` | ≤ 1024 字符 |
| `description` | **不能包含 `<` 或 `>`**（尖括号） |
| `compatibility`（可选） | 字符串，≤ 500 字符 |

> ⚠️ **`description` 不能有尖括号**这条最容易踩 —— 想写"当用户说 `<模块名>` 时"就会中招。
> 改用「」或反引号。

---

## 三、项目约定（违反 → **警告**，不阻断）

这些不影响能否装，但影响**能不能被正确调起**和**会不会腐化**。

| 规则 | 为什么 |
|---|---|
| **`description` 必须含用户会说的原话**（用引号包住的一串） | 它是 skill 被调起的**唯一依据**。写不出原话，说明触发场景还没想清楚 —— 或者这个 skill 不该存在 |
| **单个 `SKILL.md` ≤ 200 行** | skill 比文档更该短：它每次都会被完整读进上下文。超出就把细节移进 `docs/`，只留步骤和指针 |
| **正文里引用的相对路径必须存在** | 文件改名、脚本换参数、模块增删都会让它**静默失效** |
| **要有「验证」或「排查」小节** | 没有的话，跑完了也无法判断对不对 |
| **不写通用编程知识** | 只写**本项目特有的、违反直觉的**。"Spring 事务怎么用"不该出现在这里；"改了 `vm/` 必须 `mvn install` 才生效"该出现 |
| **不写知识，只写步骤和指针** | 知识在 `docs/`。抄一份就有两份，就会分叉 |
| **⚠️ 别在 skill 里写占位符字面量** | 见下 |

### ⚠️ 占位符字面量：两种写法都会出事

模板仓里写 `@@` 包起来的变量名，**两种后果都不好**：

| 写法 | 后果 |
|---|---|
| 写**真实变量名**（如 `APP_CLASS` 那个占位符） | 实例化时**会被替换掉** —— 句子语义直接反了。实测踩过：`"不填会留下 @@APP_CLASS@@"` 会变成 `"不填会留下 AcmeApplication"` |
| 写**不存在的名字** | `init.mjs --check` 报"未定义的占位符"，**挡住整条门禁** |

**所以：描述占位符这件事时，用文字说（"占位符"/"未替换的占位符"），不要写出那个语法。**
真需要举例，`@@KEY@@` 是被 `init.config.mjs` 的 `IGNORE_PLACEHOLDERS` 放行的唯一安全写法。

### 行数上限为什么是 200 而不是 400

`docs/` 那条是"超过 400 行必须拆"。skill 的门槛更低，因为：

- 文档是**按需读**的，skill 是被**完整读入上下文**的
- skill 的价值在**编排**，不在信息量 —— 信息量大的部分本来就该在 `docs/`

## 四、骨架

```markdown
---
name: <kebab-case，动词开头>
description: <做什么>。当用户说"<用户的原话 1>"、"<原话 2>"时使用。
---

# <中文标题>

<一句话：这个 skill 的前提 / 核心原则>

## 一、<步骤名>

<做什么 + ⚠️ 坑>

## 二、<步骤名>

## 排查

- **<现象>** → <原因与动作>

## 汇报

<固定结构；没做的事不要写成做了>
```

---

## 五、写法要点

### `description` 是唯一的路由依据

Claude 靠它决定"这个请求该不该用这个 skill"。所以：

- 写**用户会怎么说**，不是"这个 skill 能干什么"
- 触发词用引号包住，能写几个写几个（覆盖不同说法）
- ⚠️ **别和别的 skill 重叠** —— 重叠就意味着路由会打架。
  已知一处：Claude Code 内置的 `run` 与 `start-project` 重叠，靠写清分工缓解

### 知识放 `docs/`，skill 只放指针

反例是 `new-module` 里那段"三种选项来源"的表格 —— `docs/生成器/校验规则.md` §2 里已经有了。
**抄了两份就会分叉。** 正确写法是"按 `docs/生成器/校验规则.md` §2 决定选项来源"。

### 引用用相对路径

`docs/<文档>.md`、`scripts/<脚本>.mjs`、`backend/<模块>/` —— 这样**引用体检**才查得到。
（`node scripts/ref-check.mjs`，它管全仓的 `.md` / `.txt`，不只 skill）
别写绝对路径，也别写"某个脚本"这种指代。

## 六、体检

```bash
node scripts/skill-lint.mjs          # 只报问题，有【硬约束】违规则 exit 1
node scripts/skill-lint.mjs --all    # 连引用的那 39 个一起查（默认跳过）
node scripts/skill-lint.mjs --verbose
```

它**同时检查 `.claude/commands/`**（斜杠命令），但规则松得多 ——
命令的 frontmatter 规范没有权威依据可查，写严了全是误报。
所以只拦一种真会出事的情况：**frontmatter 坏了或缺 `description`**，
那样命令会**静默不出现** —— 用户以为敲了 `/commit`，其实什么都没发生。

**严重程度是刻意分开的**：

- **硬约束违规 → exit 1** —— skill 会装不上或静默失效，必须修
- **项目约定违规 → 只警告** —— 是质量问题，不阻断提交

与 `element-plus-scan.mjs --check` 同一个思路：**代价不对称的，处理方式就该不对称**。

> 新写或改完 skill，跑一次 `skill-lint`。它已加进 `.claude/settings.json` 的 `permissions.allow`，不用确认。
