# 文件存储：本地磁盘 / MinIO 可切换

> 两种模式由 `file.storage.type` 切换（`local` 默认 / `minio`）。
> **对外 URL 形状在两种模式下完全一样**，都是 `/profile/upload/2026/09/14/x.png`。
> 所以前端不用改、数据库里存的值不用改、存量文件不受影响。

## 为什么 MinIO 模式仍走 `/profile/**` 代理

这是本篇最需要理解的一件事——否则会以为「代理」是新引入的一层成本。

**不是。那一跳本来就在链路里。**

`frontend/vite.config.ts` 只代理 `/dev-api`，所以前端的
`VITE_APP_BASE_API + "/profile/upload/x.png"` = `/dev-api/profile/upload/x.png`
→ 经 Vite 转发到后端 `/profile/upload/x.png`。生产环境同理（`/prod-api` 由反向代理转）。
**也就是说 `/profile/**` 的流量本来就全部经过后端。**

所以这次改动不是「新增一次代理跳转」，而是**把本来就在链路里的那一跳，
从「向后端要本地静态文件」换成「后端亲自去对象存储取」**。

换来的是：

- **前端零改动**。前端有 5 处拼 `VITE_APP_BASE_API` 的逻辑，其中
  `FileUpload`、富文本 `Editor`、用户头像这 3 处**没有 `isExternal` 兜底** ——
  后端一旦返回绝对 URL，它们会拼成 `/dev-apihttps://minio.../x` 而彻底坏掉。
- **数据库零改动**。库里存的一直是相对路径，MinIO 模式下还是它。
- **预签名 URL 的根本问题被绕开**。预签名会过期，**根本不能存进数据库**；
  要存就得改成「存 object key、读取时现签」，那要动所有读路径（列表、Excel 导出）。
- **现成的安全设施全部继承**：`SecurityConfig` 对 `/profile/**` 的匿名放行、
  `RefererFilter` 防盗链。

代价：文件流量过后端。对后台管理系统量级来说可以接受；
真要直连，见下方「如果确实需要直连」。
（`ImageUtils.readFile` 里 `url.startsWith("http")` 那条分支**刻意保留**，
它就是将来直连方案的接口。）

## object key 怎么算

两者的映射是**可推导**的，所以不需要在数据库里多存一个字段：

| 磁盘绝对路径 | 对象键（MinIO 里的） | 对外相对路径（入库的） |
|---|---|---|
| `<profile>/upload/2026/09/14/x.png` | `upload/2026/09/14/x.png` | `/profile/upload/2026/09/14/x.png` |

规则就一条：**对象键 = 相对路径去掉 `/profile` 前缀**。

实现收口在 `FileStoragePath`（`@@JAVA_PACKAGE_ROOT@@.common.storage`）——
**两种存储实现都必须走它**，不允许各算各的。原因见下方「坑」第一条。

## 两种模式的接线

| 部件 | 本地模式 | MinIO 模式 |
|---|---|---|
| `FileStorageService` 实现 | `LocalFileStorageService`（`@@MAVEN_ARTIFACT_PREFIX@@-common`） | `MinioFileStorageService`（`@@MAVEN_ARTIFACT_PREFIX@@-storage-minio`） |
| `/profile/**` 谁来服务 | `LocalFileResourcesConfig` 注册的 **resource handler** | `MinioProfileController` **代理转发** |
| 条件注解 | `type=local`（`matchIfMissing`，不配也是它） | `type=minio` |

⚠️ **两边必须严格互补。** 两个提供者同时注册**不报错**——
`@RequestMapping` 的 order 是 0，resource handler 是 `LOWEST_PRECEDENCE - 1`，
所以 controller 会**静默赢过** resource handler，只是本地文件的
ETag / 条件 GET / Range 悄悄失效。**验收时要看响应头，只看 200 验不出来。**

## 切换

### 切到 MinIO

```bash
# 1. 起 MinIO（compose 里已含 minio + minio-init 两个服务）
docker compose -f deploy/docker-compose.yml up -d
docker ps -a | grep minio-init          # 应为 Exited (0)；非 0 就去看它的日志

# 2. 确认 @@MAVEN_ARTIFACT_PREFIX@@-admin/pom.xml 里有 @@MAVEN_ARTIFACT_PREFIX@@-storage-minio 依赖
# 3. 改 application.yml
#      file.storage.type: minio
# 4. 重新打包重启（改 yml 属于改后端，必须重新打包）
mvn -f backend/pom.xml clean install -DskipTests
```

启动日志里应出现 `对象存储就绪：http://127.0.0.1:@@MINIO_PORT@@ / 桶 <项目>-files`。

### 切回本地

把 `type` 改回 `local` 即可，数据不用动。

> ⚠️ **但 MinIO 里已有的文件本地没有** —— 切回去之后那些文件会 404。
> 要一起搬回来：`mc mirror` 反向拉一次（见下）。

## 存量文件的回退（`fallback-local`）

老项目切到 MinIO 时，历史文件还在本地磁盘上、不在 MinIO 里。
`fallback-local: true`（默认）让**读和删**在 MinIO 报 `NoSuchKey` 时委派给本地实现。

- **写永远进 MinIO** —— 否则新旧数据持续分叉，迁移永远做不完
- **读和删都回退** —— 不回退删的话，换头像时旧文件永远删不掉、磁盘只增不减
- 回退命中日志用 `debug`（一个列表页 20 张老图就是 20 行 `info`，会把人逼得关掉日志）

### ⚠️ 回退开着 ≠ 迁移完成

这是**过渡手段，不是终态**。正因为它让老图立刻还能看，很容易就没人去迁移了；
等到换机器部署、清理 `uploadPath/`、或者把后端容器化（本地目录不挂载）时，
老图会集体 404 —— 而那时已经没人记得曾经有过本地文件。

迁移就是搬目录，一条命令：

```bash
# 把本地 profile 下的内容整棵搬到 MinIO 桶里（桶内结构与 /profile 之后的部分一致）
docker run --rm --network <compose网络> -v "$PWD/uploadPath:/src" \
  -e MC_HOST_t=http://<账号>:<密码>@@@PROJECT_SLUG@@-minio:9000 \
  minio/mc:RELEASE.2025-04-16T18-13-26Z \
  mc mirror --overwrite /src t/@@PROJECT_SLUG@@-files
```

迁完把 `fallback-local` 改成 `false`（少一次必然落空的 `statObject`）。

## 设计取舍

### 为什么 MinIO 实现放在独立模块，而不是塞进 `@@MAVEN_ARTIFACT_PREFIX@@-common`

MinIO SDK 会拖进 guava / okhttp / jackson / bouncycastle / snappy / commons-compress
等一批传递依赖（jar 体积实测 +18MB）。**模板不该让用不到对象存储的项目背上这些。**

所以：接口与本地实现无条件在 `@@MAVEN_ARTIFACT_PREFIX@@-common`，
MinIO 实现单独一个模块。不需要的项目**删 `@@MAVEN_ARTIFACT_PREFIX@@-admin/pom.xml` 里那一行
dependency 即可**，其余一行都不用动。

### 为什么桶由 `minio-init` 容器建，而不是后端启动时建

建桶需要管理权限。后端来建，后端的凭据就必须是 root 级的；
而且文件存储是**旁路能力**，不该让「MinIO 抖动」阻断整个后台启动。

`minio-init` 一次性容器把这个两难直接消掉，也让 `docker compose up -d` 之后
**不管后端有没有起过**都能得到一个桶齐备的 MinIO。

代价：它是本仓库**唯一** `restart: "no"` 的服务，与「每个服务都带 unless-stopped」
的既有约定不一致 —— 那条约定是给长驻服务写的，一次性容器套用它反而会让它无限重启。

### 为什么后端启动只警告、不因为连不上 MinIO 就退出

文件存储是旁路：登录、CRUD、报表都不依赖它。
连不上就阻断启动，等于 MinIO 一抖动整个后台不可用。

代价是「桶不存在」要到第一次上传才暴露（报 `NoSuchBucket`）。
所以启动时会**探测一次**并给出明确日志，把排查线索提前告诉你。

### 为什么 Excel 导出仍写本地磁盘

导出流程是「写临时文件 → 下载 → 删」。把它推进对象存储，等于每次导出多两次网络往返、
零收益。代价是**后端多副本时它本来就是坏的**（A 节点写、B 节点下）——
这是既有问题，对象存储不修复它。

## ⚠️ 坑

### 对象键与本地路径必须同源，否则「上传成功但图裂」

原来的路径推导里有个 `@@CONFIG_CLASS@@.getProfile().length() + 1`，
硬编码了「profile 与子目录之间恰好一个分隔符」。当 `RUOYI_PROFILE` 带尾斜杠
（`D:/app/uploadPath/`，很常见）时，它会产出 `/profile//upload/...` —— **双斜杠**。

本地模式下 Spring 会把 `//` 规范化掉，所以这个 bug 一直没暴露；
**但对象存储不会**：`/upload` 与 `upload` 是两个不同的键，
上传写进去的和代理读出来的对不上。症状是「接口返回 200、URL 看着正常，但图裂」。

现在两种实现都走 `FileStoragePath`（唯一实现，`normalize()` 会压掉连续斜杠、
统一反斜杠、掐掉首尾斜杠）。

### `type` 拼错会启动失败——这是**好事**

`file.storage.type` 写成 `minioo` 之类，两边的条件都不成立，
于是没有 `FileStorageService` bean，启动直接失败：

```
Field fileStorage in ...CommonController required a bean of type
'...common.storage.FileStorageService' that could not be found.
```

**看到这个报错别怀疑 MinIO 没起来** —— 它说的是配置值不认识。
同理：删了 `@@MAVEN_ARTIFACT_PREFIX@@-storage-minio` 依赖却还写着 `type: minio`，也是这条。

### MinIO 的 endpoint 用 `127.0.0.1`，别用 `localhost`

compose 把端口只绑在 IPv4 的 `127.0.0.1` 上，
而 Windows 上 `localhost` 常先解析到 `::1`（IPv6）。
症状是 `Connection refused`，且**看不出是 IPv6 的锅**。

### 上传报 `NoSuchBucket`

桶没建成。排查顺序：

```bash
docker ps -a | grep minio-init      # 看退出码和日志；不是 Exited (0) 就是它的问题
docker logs <项目>-minio-init
```

另一个常见原因是**桶名不一致**：compose 里写一个、`application.yml` 里写另一个。

> 桶**必须是私有的**。绝不要为了让前端直连而加 `mc anonymous set download` ——
> 那会绕过 `SecurityConfig` 的匿名放行范围与 `RefererFilter` 防盗链，
> 等于把「走代理」换来的所有好处又扔回去。

### `compose` 里引环境变量要写 `$$`，不是 `$`

`docker compose` 会在**宿主机**上先对单个 `$VAR` 做插值。
`minio-init` 的 entrypoint 里若写 `"$MINIO_ROOT_USER"`，宿主机上没这个变量 → 变成空串
→ `mc alias set` 用空凭据「成功」建立别名，然后建桶 `Access Denied`。

写成 `"$$MINIO_ROOT_USER"` 才会原样传给容器内的 shell 展开。
（这个坑实跑才发现：日志看着像权限问题，实际是插值。）

### 上传有两道大小闸门，别混

- `spring.servlet.multipart.max-file-size`（`application.yml`，默认 10MB）——**更早**，进 Controller 前就拦
- `FileUploadUtils.DEFAULT_MAX_SIZE`（代码层，50MB）

排「为什么传不上去」时先确认是哪一道拦的，两者报错信息不同。

### 文件类规则只在前端生效

`validation_rule` 里的 `limit` / `fileSize` / `fileType` **只在前端生效**，服务端不校验。
服务端只有上面那两道全局闸门（白名单 + 大小）。
要按字段校验，得让上传接口知道字段归属——那是另一件事，当前没做。

## 如果确实需要直连 MinIO

将来若要绕开后端（大文件、高并发），需要同时处理三件事，缺一不可：

1. 前端那 3 处没有 `isExternal` 兜底的拼 URL 逻辑（`FileUpload` / `Editor` / `userAvatar`）
2. 数据库里的值：预签名 URL 会过期，必须改成「存 key、读取时现签」，
   于是所有读路径（列表渲染、Excel 导出、富文本内容）都要跟着改
3. 桶的访问控制与防盗链要重新设计（现在的匿名放行只覆盖 `/profile/**` 这个路径）

`ImageUtils.readFile` 里 `url.startsWith("http")` 那条分支就是为这种情况留的口子。
