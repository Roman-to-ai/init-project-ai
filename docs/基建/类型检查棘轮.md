# 类型检查：棘轮，不是全绿门禁

```bash
node scripts/typecheck.mjs            # 只报【新增】错误；有新增则 exit 1
node scripts/typecheck.mjs --update   # 把当前结果写为新基线（修完错误后收紧）
node scripts/typecheck.mjs --list     # 列出当前全部错误
```

## 为什么是棘轮

本仓库有 **436 个存量类型错误**（基线见 `scripts/typecheck-baseline.json`），
一次性修完要动 30+ 个文件。但**直接跑 `vue-tsc` 会淹没在存量噪音里**——
没人能从 400 多行输出里看出「我刚才是不是改坏了」。

棘轮解决的问题：把存量记进基线，之后**只对新增错误失败**。

- 你**不能让它变多** —— 改坏东西立刻被发现
- 它会随你减少而**收紧** —— 修掉一个就跑 `--update` 把基线降下来

## 存量错误长什么样（按基线实测）

**按错误码**：

| 数量 | 错误码 | 含义 |
|---|---|---|
| 203 | `TS2322` | 类型不可赋值（模板绑定签名、`undefined` 未处理） |
| 121 | `TS2339` | 属性不存在（多半是 `queryParams.params` 这类模板没声明的字段） |
| 27 | `TS18048` | 值可能为 `undefined` |
| 23 | `TS2345` | 实参类型不匹配 |
| 17 | `TS2367` | 比较的两个类型没有重叠（判断恒为假） |
| 15 | `TS18047` | 值可能为 `null` |
| 其余 | `TS2353` / `TS7053` … | |

**按目录**：`src/views/` 378、`src/layout/` 34、`src/components/` 22。

> **绝大多数集中在 `src/views/`** —— 因为生成器产出的 CRUD 页面就是这个写法，
> 每个模块约带 22 个。清理时从 `src/layout/` 和 `src/components/` 入手最划算：
> 量少、手写、修完不会再生。

**没有配置捷径**：关掉 strict 只是把数量降下来一截，问题本身还在。

## key 为什么不带行列号

带行列号的 key 在改动后会大面积漂移（文件里插一行，后面所有错误的行号全变），
于是每次改代码都报一堆假的「新增」。所以 key 只取 `文件名 + 错误码 + 消息`，
配合数量做多重集比较。**行号只用于展示。**

### 一个已知局限：消息里嵌类型字面量的错误仍会 churn

生成代码里 `form.value = response.data` 这类报错，消息中会列出目标类型的字段顺序：

```
Type 'X | undefined' is not assignable to type '{ a?: number; b?: string; ... }'
```

一旦调整 `gen_table_column.sort`（列顺序）或增删字段，这段消息就变，于是棘轮报
「新增 1 个 / 修复 1 个」——**净变化为 0，是假警报**。

判断方法：**看新增与修复的数量是否相等且文件名相同。是则跑 `--update` 即可。**

## ⚠️ 坑

### 一个语法错误会让 `vue-tsc` **只报那一个错误**

**这是最容易误判的一条。** 只要工程里有**任何一处语法错误**（`TS1109` 之类），
`vue-tsc` 会中止整个程序，**不再报告其余任何类型错误**。

实测：`frontend/vite.config.ts` 里 `port: @@FRONTEND_PORT@@` 是模板占位符
（不是合法表达式）时，`vue-tsc --noEmit` 只报 1 个错误；把那两处换成合法值后，
**436 个错误全部回来**。

所以当棘轮报出「新增 1 个 / 修复 436 个」时，**那不是"代码质量突飞猛进"，
而是类型检查被一个语法错误整体掐掉了**。

> **判断方法**：看新增的那一个错误是不是 `TS1109` / `TS1005` 这类**语法**错误。
> 是的话，先修它，再看真实的错误数。

### 模板态下这个检查现在也能跑了（2026-09-15 修复）

原先模板仓里 `vite.config.ts` 的 `port: @@FRONTEND_PORT@@` 是**表达式位置**的占位符，
**必然命中上面那条** —— 于是模板态的 `typecheck` 等于没有，数字没有意义。

**已修**：那一行改成 `port: Number("@@FRONTEND_PORT@@")`。
模板态算出来是 `NaN`（模板从不运行），实例态是 `8082` —— **两边都是合法 TS**。
前端其余 4 个含占位符的文件本来就在**字符串里**，不受影响。

实测：模板态现在跑出 **426** 个错误（基线 436 是在实例态录的）——
✅ 无新增、🎉 修复 10 个。那 10 个的差来自两态占位符取值不同。

> **基线保持在实例态（436）不动**：模板态只会"多报修复"，**不会误报新增**；
> 而真新增的错误照样会被抓住。所以两态都能用，不需要两份基线。
>
> ⚠️ **千万不要在这种情况下跑 `--update`** —— 那会把基线压成 1，
> 等语法错误修好后，436 个真实错误会全部变成「新增」。

### `declare module 'vue'` 差点让这套检查永远看不见

`src/types/global.d.ts` 原先是**非模块** `.d.ts`（没有顶层 import/export）。
在这种文件里写 `declare module 'vue'` **不是类型增强，而是整体替换** vue 的类型 ——
`vue-tsc` 的模板类型检查随之整体塌陷成 `any`，把问题全遮住了
（当时跑出来只有 8 个）。

> **规则：给自带类型的包写 `declare module` 是破坏性的**（把人家好好的类型抹成 `any`）。
> 只有确实不带类型的包才在该文件里声明。判断：
>
> ```bash
> node -e "console.log(require('./node_modules/<包名>/package.json').types)"
> ```

**增强 vue 全局属性请改 `src/types/vue-augment.d.ts`** —— 那里是**模块**文件，有 `export {}`。

### 依赖没装好时它连启动都做不到

`frontend/node_modules` 残缺时，报的是
`找不到 vue-tsc：…/vue-tsc/bin/vue-tsc.js`。修法：

```bash
pnpm -C frontend install
```

> 另：`@types/node` 一度**从未安装**，而 `tsconfig.json` 声明了 `types: ["node"]` ——
> 于是 `vue-tsc` 连启动都做不到（`TS2688`）。Vite 不做类型检查，
> 业务一直正常，把这个缺陷掩盖了很久。

## 设计取舍

### 为什么不修完存量再上棘轮

修完 436 个错误是一个跨 30+ 文件的项目，不是一步能做完的事。
在此之前，**没有任何自动化手段能发现「这次改动引入了新的类型错误」**。
棘轮的价值在于：立刻就有保护，且保护范围随时间自动收紧。

### 为什么不改 VM 模板去迎合类型

代码生成器产出的 CRUD 页面每个模块约带 **22 个类型错误**，性质与存量完全同类
（`proxy` 可空、`reset()` 赋 null、`queryParams.params` 未声明、`@click` 签名）——
那是框架全代码库的统一写法。

**刻意不去改 VM 模板迎合类型**：那会让生成代码与其余代码库风格分裂，
而且其中几处改动（如 `reset()` 的初值）会**改变运行时行为**。
把它收进基线，让棘轮继续对**手写改动**敏感即可 —— 回归本来就主要来自手写改动。
