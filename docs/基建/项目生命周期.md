# 项目生命周期

> **什么时候读**：新起一个项目时通读一遍；做到某个阶段时回来看那一段该做什么。
>
> 这篇讲**做事的顺序和各阶段的完成标志**。具体怎么做在对应的 skill 里，这里不重复。

## 两条主线

```
0 → 1   从零到一个能演示的系统        阶段 0~3
1 → 10  从能用到能交付、能长期维护    阶段 4~8
```

**每个阶段都有一个「完成标志」，是可验证的** —— 达不到就别进下一阶段。
这是这套东西的核心纪律：**不靠"感觉差不多了"，靠能跑一遍的东西。**

---

## 0 → 1

### 阶段 0 · 立项（约半天）

**做**：定标识 → 复制模板 → 实例化 → 体检 → `git init` → 起环境

**喊**：`/init-project`

**三个最容易踩的**：

- **`MAVEN_ARTIFACT_PREFIX` 别漏** —— 它不在"必须填"那类里（有默认值 `app`），
  但决定**所有模块目录名和 jar 名**。漏了你的项目一半叫 `app-*`
- **先查端口再定** —— 默认那组（3307/6380/9002/9003/8080/80）**也是另一个实例的默认值**，
  同机跑第二个项目必然撞
- **复制时排除** `node_modules` / `target` / `.ai-log` / `docs/业务` ——
  前一类是依赖产物，后一类是**模板自己的历史与生成物**

**完成标志**：能打开登录页、`admin` 登进去、菜单空白 —— **一个能跑的空系统**。

### 阶段 1 · 领域建模（约 1~2 天）

**做**：把业务需求变成**表设计**。**这一步决定后面全部。**

**喊**：`/task-brief`（先把需求说清楚）→ `/design-schema`

**产出**：一份**建表 SQL + 生成器配置表**，能直接喂给阶段 2。

> ⚠️ **最值得花时间的一步。** 表设计错了后面全是返工 —— 生成物、菜单、权限、
> 前端页面都跟着错。宁可在这里多问几轮。

### 阶段 2 · 第一个模块（约 1 天）

**做**：拿阶段 1 的产物走生成器，跑通一条完整的链。

**喊**：`/new-module` → `/verify-module`

**最容易漏的两步**（都在 `new-module` 里写着）：

- **合并 barrel**（`frontend/src/types/api/index.ts`）—— 漏了页面 import 类型会报错
- **`parentMenuId` 别用默认值** —— 生成器默认挂到「系统工具」下，业务模块不该在那儿

**完成标志**：菜单可见、列表能查、增删改查各点一遍都对。

> **第一个模块是整条链的验证。** 它通了，后面就是重复。

### 阶段 3 · 滚模块 + 补自定义（MVP 收口）

**做**：阶段 1→2 循环把业务铺完；生成器做不了的用手写补。

**喊**：`/design-schema` → `/new-module`（循环）· `/backend-code` · `/frontend-component`

**什么该手写**（生成器覆盖不到的）：审批/批量导入/状态流转这类业务动作、
多表 join 与聚合、跨切面能力（文件存储这类）。

**完成标志**：**能给人演示了** —— 业务走通、页面能点。

## 1 → 10

### 阶段 4 · 权限与角色

**做**：从"只有 admin 能用"到"不同角色看到不同东西"。

**要点**：

- ⚠️ **生成的菜单 SQL 不含 `sys_role_menu`** —— admin 不受影响，
  但**其他角色看不到新菜单**，要自己补
- **权限串三处逐字对齐**：`@PreAuthorize` ↔ `sys_menu.perms` ↔ `v-hasPermi`。
  对不上就是按钮不显示（缺记录）或 403（串不一致）—— **两种症状两种病**
- **改完权限必须重新登录** —— 缓存在 Redis

**完成标志**：换一个非 admin 角色登录，菜单和按钮**按预期增减**。

### 阶段 5 · 质量收口

**做**：把存量问题收进基线，让门禁真正起作用。

**喊**：`/verify-module`

**要点**：跑六道门禁（见 `README.md` 的「提交前跑一遍」），
把当前状态用 `--update` 记成基线，之后**只对新增失败**。

**完成标志**：门禁全绿；`.gitlab-ci.yml` 挂上去能跑。

> ⚠️ 这套东西**没有单元测试** —— 质量靠的就是这几道门禁 + 人工验证。

### 阶段 6 · 交付

**喊**：`/release`

**要点**：

- 打包用 `build:prod`（**不是 `build:stage`** —— 接口前缀不一样）
- ⚠️ **生产配置检查**：**换掉 JWT 密钥**、端口、上传路径、前端接口前缀
- 交付物里 **`backend/sql/` 有导入顺序**，顺序错了会中途停下、后面全不执行
- **打 tag 留回滚点**

**完成标志**：别人拿到包**能跑起来**。

### 阶段 7 · 运维与排查

**喊**：`/troubleshoot` · `/db-manage`

**要点**：

- 出问题**先收集证据再动手** —— "可能是 X，我改改看"是最贵的排查方式
- 改库结构走 `upgrade_<日期>_<描述>.sql`，**不要动基线种子**；**改前先备份**
- 新踩的坑**就近写进对应文档的 `## ⚠️ 坑`** —— 不记的话下一个人会再踩一次

### 阶段 8 · 长期维护

**做**：让系统**不随时间腐化**。

| 每次改动后 | 喊 |
|---|---|
| 更新文档 | `/update-docs` |
| 记变更日志 | `/ai-changelog` |
| 提交 | `/commit` |
| 模板有改进、想同步 | `/sync-ai-layer` |

**完成标志**：半年后回来，**文档还准、门禁还有效、新人能靠 `docs/` 上手**。

---

## 横切：每次动手的固定动作

**这是这套东西真正的核心。** 顺序固定，不要跳：

```
开工前   /task-brief     把需求交代清楚（要什么 / 上下文 / 验收标准 / 边界）
   ↓
做       对应的 skill     让 skill 带步骤 —— 别自己编排顺序
   ↓
收尾     六道门禁  →  /verify-module  →  /update-docs  →  /ai-changelog  →  /commit
```

单次改动看起来变慢了，但它换来的是**下一个人（或下个月的我）能接得上**。

---

## ⚠️ 这套东西不覆盖什么

**这些得自己做，别以为模板会管**：

| | 说明 |
|---|---|
| **远程生产部署** | 反向代理、HTTPS、进程守护、监控告警 —— 只到"能打出一个可交付的包" |
| **单元测试 / 集成测试** | 原项目就没有，靠门禁 + 人工验证替代 |
| **定时任务** | 有 Quartz 模块和 `Crontab` 组件，但**没有 skill** |
| **前端非 CRUD 页面** | 生成器只出列表页；仪表盘/详情页/向导**没有 skill** |
| **多环境管理** | dev / staging / prod 的配置分发没做 |
| **数据迁移** | 只有"改结构走 upgrade 脚本"的约定，没有迁移框架 |

> 前两条是**刻意的取舍**（见 `AI工程化需求.txt` §3.6、§3.19）；
> 中间两条是**已知的缺口**，用之前要有心理准备。
