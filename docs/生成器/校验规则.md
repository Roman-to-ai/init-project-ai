# 校验规则（validation_rule）

> **配 `validation_rule` 时查这一篇。** 能配哪些键、前后端各认哪些、

## 1. 规则键的真实覆盖 ⚠️ 本篇最该看的一张表

`validation_rule`（JSON）里的键，**前端和后端覆盖不一样**——这是最容易踩的地方：

| 规则键 | 前端表单 | 后端校验 | 说明 |
|---|---|---|---|
| `required` | ✅ | ✅ | 也可用生成器界面上的 `is_required` |
| `pattern` / `patternMessage` | ✅ | ✅ | 值就是正则字面量 |
| `min` / `max` / `precision` | ✅ | ✅ | 前端只当 `el-input-number` 属性；`rate` 用 `max` |
| `maxLength` | ❌ | ✅ | **用户能随便输超长，提交才被后端打回** |
| `allowNegative` | ❌ | ✅ | 同上 |
| `gtField` `ltField` `eqField` `neField` | ❌ | ✅ | **跨字段校验前端完全没有**，提交才知道错 |
| `fileSize` / `fileType` / `limit` | ✅ | ❌ | **服务端不校验**，绕过前端直接调接口就失效 |
| `step` | ✅ | ❌ | 纯组件属性 |
| `treeApi` `valueField` `labelField` `parentField` | ✅ | ❌ | 纯前端配置 |
| `options` `optionsApi` `optionLabel` `optionValue` | ✅ | ❌ | 纯前端配置。**选项来源**，见 §2 |
| `multiple` | ✅ | ⚠️ 生成期 | `select` / `treeselect` 的多值开关。它也**驱动生成期**（决定挂不挂 `@MultiValue`、查询区出不出多选），但 `FieldRule` 不认识它 —— 转换靠生成期写进实体的注解，不是运行时 |
| `displayColumn` | ✅ | ⚠️ 生成期 | 冗余显示列：本表存关联对象名称的列（写 javaField）。见 `表与关联.md` |
| `refTable` / `refValueColumn` / `refLabelColumn` | ❌ | ⚠️ 生成期 | 后端算名称要的关联表与两个列名 —— **数据库列名**，与 `labelField`/`valueField`（接口返回的 JSON 键）**不是一回事** |
| `junctionTable` / `junctionMainFk` / `junctionRefFk` / `idsField` | ✅ | ⚠️ 生成期 | 多对多的**辅助表**四件套：中间表名、它的两个外键、实体上的瞬时 id 字段。见 `表与关联.md` §4 |
| `pickerColumns` | ✅ | ⚠️ 生成期 | 表格选择器要展示的列（`标签:字段名`，用 `\|` 分隔）。`treeselect` 默认就用选择器；选项来自接口的要显式配它才用。见 `表与关联.md` §2 |

> ⚠️ 这张表分两半：**上半区**是前后端都管的校验；从 `treeApi` 起的那几行是**纯前端配置**，
> 后端不认识它们（`FieldRule` 忽略未知键）。所以 `validation_rule` 这个名字**名不副实** ——
> 它实际装的是「**字段扩展配置**」：校验规则 ＋ 选项来源 ＋ 多值开关。
>
> `multiple` 那行的「生成期」是唯一的特例：它不参与运行时校验，但**决定生成出来的实体挂不挂
> `@MultiValue`** —— 多值字段的线上形状（JSON 数组）就是靠那个注解兜住的。见 `模板增强清单.md`。

**不存在、别配**（配了没有任何效果，也不会报错）：

| 键 | 状态 |
|---|---|
| `minLength` | 前后端都没实现 |
| `unique` | 前后端都没实现。唯一性现在只能靠**数据库唯一索引**兜 |
| `suffix`（单位后缀） | 没实现，如「元」「kg」 |
| `placeholder` / `default` / `readonly` | 没实现 |
| `minDate` / `maxDate` / `allowFuture` / `allowPast` | 没实现 |
| `requiredIf`（条件必填） | 没实现 |

## 2. 规则 JSON 怎么写

写在 `gen_table_column.validation_rule`（`varchar(2000)`）：

```sql
UPDATE gen_table_column c JOIN gen_table t ON t.table_id = c.table_id
SET c.validation_rule = '{"required":true,"maxLength":64}'
WHERE t.table_name = '你的表' AND c.column_name = 'product_code';
```

常用组合（**这张表就是「业务语义 → 怎么配」的对照**）：

| 场景 | validation_rule |
|---|---|
| 编码，必填且 ≤64 字 | `{"required":true,"maxLength":64}` |
| 手机号 | `{"pattern":"^1[3-9]\\d{9}$","patternMessage":"手机号格式不正确"}` |
| 邮箱 | `{"pattern":"^[\\w.+-]+@[\\w-]+\\.[A-Za-z]{2,}$"}` |
| 年龄 0~150 整数 | `{"min":0,"max":150,"precision":0}` |
| 金额，非负两位小数 | `{"min":0,"precision":2}` |
| 折扣率 0~100 | `{"min":0,"max":100,"precision":2}` |
| 评分（5 星制） | `{"max":5}`（配 `rate` 控件） |
| 结束时间晚于开始 | `{"gtField":"startTime"}`（值写**同类里的 javaField 名**） |
| 单图，≤2MB，限 png/jpg | `{"limit":1,"fileSize":2,"fileType":"png,jpg"}` |
| 多附件，最多 3 个 | `{"limit":3,"fileSize":10,"fileType":"pdf,doc,docx"}` |

> ⚠️ **JSON 里的反斜杠要写两层**（`\\d`）——`validation_rule` 是 JSON 文本，
> 一层会被 JSON 解析吃掉。SQL、文档、生成器界面里都要小心。

### treeselect 的四个键必须配全

唯一需要数据源的类型，缺一个控件就不可用：

```json
{
  "treeApi": "/biz/demoCategory/list",
  "valueField": "categoryId",
  "labelField": "categoryName",
  "parentField": "parentId"
}
```

`treeApi` 是**返回扁平列表**的接口，前端用 `proxy.handleTree` 建树 ——
所以接口返回数组即可，**不需要后端返回树结构**。

### 选择类控件的三种选项来源

`select` / `radio` / `checkbox` 的选项可以来自三个地方，**优先级从上到下**：

| 来源 | 配在哪 | 适合什么 |
|---|---|---|
| **字典**（优先级最高） | `gen_table_column.dict_type` | 稳定的枚举，多个模块复用 |
| **写死代码** | `validation_rule.options` | 一次性的小枚举（是/否、启用/停用），不值得建字典 |
| **接口** | `validation_rule.optionsApi` | 会变的数据（部门、设备、物料、客户） |

```json
{"options":[{"label":"启用","value":"1"},{"label":"停用","value":"0"}]}
{"optionsApi":"/biz/demoCategory/list","optionLabel":"categoryName","optionValue":"categoryId"}
```

- `options` 是 **JSON 数组**，每项 `{label, value}`。`value` 必填；`label` 缺省为空串
- `optionsApi` 的字段映射沿用 `treeselect` 的惯例；**不配 `optionLabel`/`optionValue` 时默认取 `label`/`value`**
- 接口返回 `AjaxResult`（`{data}`）或 `TableDataInfo`（`{rows}`）**都认**

> ⚠️ `useApiOptions` 的 `value` **保持接口返回的原始类型**（ID 字段是数字就留数字）。
> 强转成字符串会让 `el-select` 拿数字 id 去比字符串选项，多选/回显直接显示裸 id
> （演示产品的「标签名称」多对多就是踩的这个坑）。

> ⚠️ **三个来源同时配了时，以字典为准**；写死与接口同时配时写死优先。
> 所以想用写死/接口，**记得把 `dict_type` 清空**，否则字典会盖掉它。

生成出来的东西：

```ts
// 写死 —— 页面里声明一次，查询区 / 表单区 / 列表区共用
const productStatusOptions = [{ label: '启用', value: '1' }, { label: '停用', value: '0' }]

// 接口 —— 页面加载时拉一次
const productStatusOptions = useApiOptions('/biz/demoCategory/list', 'categoryName', 'categoryId')
```

> 接口那股是**页面加载时就拉**，不是用的时候才拉 —— 因为**列表列也要用它把值翻译成标签**，
> 懒加载会先显示一列原始值再跳变。`treeselect` 能懒加载是因为它不出现在列表里。

列表区**三种来源都用 `<dict-tag>`** —— 它的 `options` 接受任意 `{label,value}` 数组，
所以不必为不同来源换组件。

> ⚠️ **勾了「查询」的 select/radio，查询区生成的 `:value` 不做 `parseInt`**；
> 而表单区对 `Integer`/`Long` 字段**会**做。这是两处刻意的差异（沿袭自字典分支），别去"统一"。

## 3. 为什么把规则装进一个 JSON 列

### 3.1 问题

框架原本只有 `gen_table_column.is_required` 一个约束维度。
要支撑上面那些，直觉做法是加一堆列：`min_length`、`max_length`、`pattern`、
`min_value`、`max_value`、`allow_negative`、`precision`、`file_limit`…

**但加一个列属性要改 6 处**（DDL、实体四件套、两个 Mapper.xml 共 7 个位置、
`GenUtils.initColumnField`、`synchDb` 保留白名单），**漏一处是静默失效**（详见 `模板增强清单.md`）。
加 10 个列就是 60 处改动。

### 3.2 做法：一个 `validation_rule` 列装全部约束

```json
{ "required": true, "maxLength": 64, "pattern": "^[A-Z0-9-]+$" }
{ "min": 0, "max": 150, "precision": 0, "allowNegative": false }
```

好处：

- **只加 1 个列 = 只改那 6 处**，而不是 60 处
- 将来加新约束（如 `requiredIf`）**不用再动 DDL 和 Mapper**
- AI 改起来也方便：一条 `UPDATE gen_table_column SET validation_rule = '...'` 就是一条规则
  （与 `is_common` 的 AI 工作流一致）

代价：

- SQL 里不能按单个约束筛选（如「找出所有必填字段」）—— 实际用不上
- 规则**目前只能靠 SQL 写**：`frontend/src/views/tool/gen/editTable.vue` 里没有
  `validation_rule` 的编辑入口（连前端 TS 类型 `GenTableColumn` 都没这个字段）。
  写入方式是 §2 开头那条 `UPDATE`。

> `is_required` 保持不动（向后兼容 + 界面上「必填」复选框继续用），
> `required` 在 JSON 里作为同步字段存在，**以 JSON 为准**。

### 3.3 能从 DDL 自动推导的，不要让人手填

| 约束 | 来源 |
|---|---|
| `maxLength` | `varchar(64)` → 64 |
| `precision` | `decimal(10,2)` → 2；`int` → 0 |
| `required` | `not null` 且无 `default` → true |
| `allowNegative` | `unsigned` → false；否则 true |
| `min` / `max` | 整数类型按位宽推（`tinyint` → -128~127 等） |

**只有 DDL 表达不了的才需要人配**：年龄 0~150、手机号正则、文件数量上限、
金额是否允许负数（业务决定，不是类型决定）。

## 4. 后端如何「抽离」校验

### 4.1 现状：**生成器产出的 CRUD 原本服务端零校验**

> ⚠️ 纠正一个常见误解：代码生成器产出的 CRUD **服务端零校验**。
> 生成的实体只有 `@Excel`，Controller 是 `add(@RequestBody X x)` —— **没有 `@Validated`**。
> 前端 `rules` 是唯一防线，绕过前端直接调接口就能写进脏数据。
>
> （框架自己手写的实体如 `GenTable` 是有校验的 —— 有 `@NotBlank` 和 `@Validated`。
> 所以这不是「框架不支持」，而是**生成器模板没生成**。本项目补上了。）

### 4.2 规则 JSON 作为唯一来源，后端做解释器

```
gen_table_column.validation_rule (JSON)
        │
        ├─→ 生成期：写进前端 rules     （模板读规则）
        └─→ 运行期：后端 RuleValidatedValidator 读规则校验
```

| 组件 | 位置 | 作用 |
|---|---|---|
| `FieldRule` | `@@MAVEN_ARTIFACT_PREFIX@@-common/core/validate` | 规则模型 + **校验逻辑的唯一实现处** |
| `FieldRuleProvider` | `@@MAVEN_ARTIFACT_PREFIX@@-common/core/validate` | 规则来源接口（可替换） |
| `GenFieldRuleProvider` | `@@MAVEN_ARTIFACT_PREFIX@@-generator` | 从 `gen_table_column` 读 + 缓存 + `refresh()` |
| `@RuleValidated(table)` | `@@MAVEN_ARTIFACT_PREFIX@@-common/annotation` | 类级约束，触发校验 |
| `@RuleField(column, label)` | `@@MAVEN_ARTIFACT_PREFIX@@-common/annotation` | 标记字段，label 用于拼错误消息 |
| `RuleValidatedValidator` | `@@MAVEN_ARTIFACT_PREFIX@@-common/core/validate` | 逐字段校验，错误绑定到具体字段 |

生成器模板（`domain.java.vm` / `sub-domain.java.vm` / `controller.java.vm`）**无条件**
生成 `@RuleValidated` + 每个字段的 `@RuleField` + Controller 上的 `@Validated`。

> **为什么无条件生成而不是「有规则才生成」**：这样在生成器界面上新配一条规则 →
> 保存 → 校验**立即生效**，不需要重新生成代码、不需要重启。
> 那才是「把校验抽离开代码」的意义。`@RuleField` 看起来啰嗦，但它和每个字段都有的
> `@Excel` 是同一量级。

### 4.3 实测

```
全合法                → 操作成功
适用年龄 = 200        → 适用年龄不能大于 150
含税单价 = -5         → 含税单价不能为负数
折扣率   = 999        → 折扣率不能大于 100
联系电话 = "123"      → 联系电话手机号格式不正确
一次提交 6 处违规      → 全部列出（每条都带字段名）
```

> 顺带改了 `GlobalExceptionHandler`：上游只取 `getFieldError()`（第一条），
> 用户改一个提交一次。改成一次列出全部，单条时输出与上游一致。

### 4.4 已知边界

- **规则来源是生成器配置表**（`gen_table_column`）。若生产环境不部署 `@@MAVEN_ARTIFACT_PREFIX@@-generator`，
  需要换一个 `FieldRuleProvider` 实现（接口已抽出）。
- **重新导入表会丢规则**：`删除 + 导入表` 产生全新列配置。要保留请用「同步数据库」
  （`synchDb` 的白名单里有 `validation_rule`）—— 详见 `docs/基建/数据库.md`。
- **文件类规则只在前端生效**（见 §1）。

## 5. 演进历程：当初的排期 vs 实际落地

这套东西最早是一份**提案**，下面是排期与实际结果的对照
（`git log` 里的 `P0` / `P1` / `P3` 就是这个排期）：

| 排期 | 内容 | 落地情况 |
|---|---|---|
| — | 单图/多图、单文件/多附件（`:limit` 透传） | ✅ 一并建起了 `validation_rule` 列 |
| **P0** | 数值语义类型 `number` | ✅ 上下限/步长/小数位都从规则来 |
| **P0** | 格式类：`phone` / `email` / `url` / `idcard` | ⚠️ **改了做法**：没做成独立 `htmlType`，而是 `input` + `pattern` 规则 |
| **P1** | `validation_rule` JSON 列 + 后端 `RuleField` 解释器 | ✅ 并补上了框架原本**完全没有**的服务端校验 |
| **P2** | `switch` / `month` / `year` / `rate` | ✅ |
| **P2** | `cascader` | ❌ 未做 —— 项目里没有实际需求 |
| **P3** | 跨字段校验 | ✅ `gtField` / `ltField` / `eqField` / `neField`（**但只做了后端**，见 §1） |
| **P3** | `treeselect` 关联对象 | ✅ 但**只做了树选择**，`entitySelect`（任意实体下拉）未做 |
| **P3** | 生成器界面 | ✅ 规则可在界面上直接改，**保存即生效，不用重新生成** |

### 唯一被推翻的决定

排期里 P0 的「格式类做成独立 `htmlType`」**没有照做**。真正的收益在校验不在样式，
而每加一个 `htmlType` 就要改模板的各 3 个区块（查询区 / 表单区 / 列表区）——
收益小而漏改风险大。改成 `pattern` 规则后，一种机制覆盖了手机号/邮箱/身份证/网址
全部格式校验，模板零改动。

### 分批做的教训（这条依然有效）

> ⚠️ 一次把 20 种类型全铺开风险很高：每加一个 htmlType 就要改模板的各 3 个区块。
> 本项目曾因为「只改了一个模板」踩过两次坑（`date`/`time` 漏了树表、`is_common` 漏了树表），
> 其中一次的表现是**字段在树表上静默消失**。
> 2026-09-14 单表/树表模板合并成一个文件后，这类失误在结构上不再可能 ——
> 但**合并动作本身也丢过东西**，见 `模板增强清单.md` 的「合并丢过两处树表代码」。

**分批做，每批真跑一次生成验证** —— 别只看模板文本。上面每一行 ✅ 都是一次独立提交。

## 6. ⚠️ 坑（校验规则特有的）

> 模板作者层面的坑（字段静默消失的三种成因、Velocity 的两个陷阱、树表树名列、
> 树表合并后丢过什么）**不在这里**，见 `模板增强清单.md`。

### 文件的两个 `limit` 陷阱

- **默认值是 5，不是 1**：想要「单图/单文件」必须显式写 `{"limit":1}`
- 改了默认会影响所有既有项目（从"最多 5 个"变成"只能 1 个"），属破坏性改动，**本项目刻意不改**

### 上传有三道闸门，别混

1. `spring.servlet.multipart.max-file-size`（`application.yml`，默认 10MB）——**最早**，进 Controller 前就拦
2. `FileUploadUtils.DEFAULT_MAX_SIZE`（代码层，50MB）
3. `validation_rule.fileSize`——**只在前端**

排「为什么传不上去」时先确认是哪一道拦的，三者报错信息不同。

### `switch` 存的是字符串 `'1'` / `'0'`

不是数字 `1`/`0`。建表用 `char(1)`，默认值写 `'0'`。
演示表里的 `is_recommend` 用了 `tinyint(1)` —— 那是**另一种存法**，两者别混。

### 查询区的 `BETWEEN` 只给了日期类

`date` / `datetime` 配 `queryType=BETWEEN` 会出 `daterange` 选择器。
`number` 配 `BETWEEN` **什么都不会发生**——数值区间查询没实现。
