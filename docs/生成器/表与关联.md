# 表与关联怎么设计

> **设计业务表时查这一篇**：这张表跟别的表是什么关系 → 用哪种生成模式、怎么配。
> 字段用哪个控件看 `字段类型.md`；规则怎么写看 `校验规则.md`。

## 两条贯穿全局的约定

- **关联只用 ID，不建物理外键。** `backend/sql/` 里一个 `foreign key` 都没有 ——
  生成器产出的 CRUD 不处理级联，物理外键只会让删改顺序变挑剔。
- **表名、字段名、`comment` 一个都不能省。** `comment` 是表单 label、列表列名、搜索提示的唯一来源，
  漏了就是满屏英文变量名。

## 生成模式只有三种，且互斥

| 生成模板 | 用在 | 和单表的差别 |
|---|---|---|
| **单表**（`crud`） | 独立表；**多对一 / 一对一的关联字段**也挂在单表上 | —— |
| **树表**（`tree`） | **自身父子关联** | 不分页、行内「新增」、父节点用树选择器 |
| **主子表**（`sub`） | **一对多**（主表 + 明细） | 明细内联在主表的弹窗里，可增删改 |

> 没有「树表 + 主子表」这个组合，也没有第二层明细（孙表）。

## 1. 普通表

单主键 `bigint auto_increment`，外加审计列（照 `backend/sql/biz_demo.sql` 抄）：

```sql
del_flag    char(1)     default '0'   comment '删除标志（0存在 2删除）',
create_by   varchar(64) default ''    comment '创建者',
create_time datetime                  comment '创建时间',
update_by   varchar(64) default ''    comment '更新者',
update_time datetime                  comment '更新时间',
remark      varchar(500)              comment '备注',
```

> ⚠️ 生成器**按单主键工作**：模板里只有一个 `$pkColumn`，取第一个标记主键的列；
> 一列主键都没有时它拿**第一列**顶替。所以**联合主键 / 无主键的表别直接导**。

## 2. 多对一、一对一（字段级关联，不是生成模式）

关联是**字段**的事。在关联字段上配 `treeselect`：

```json
{"treeApi":"/biz/demoCategory/list","valueField":"categoryId","labelField":"categoryName","parentField":"parentId"}
```

- `treeApi` 返回**扁平列表**即可，前端自己建树
- **一对一** = 同样的字段 + 数据库唯一索引；更省事的做法是**把字段冗余进主表**，不做关联
- **选的时候不是普通下拉**：`treeselect` 在**查询区与表单区**都用下面的**表格选择器** ——
  点开是弹窗，能搜关键字、用表格看多列。后端不用改：发的还是关联 id，走 `and col = #{id}` 等值匹配

### 表格选择器（关联字段怎么选）

```json
{"treeApi":"/biz/demoCategory/list","valueField":"categoryId","labelField":"categoryName",
 "parentField":"parentId",
 "pickerColumns":"分类名称:categoryName|显示顺序:orderNum|状态:status:biz_category_status"}
```

- `pickerColumns` 用 `|` 分隔，每段是 `字段名` 或 `标签:字段名`，想显示字典列就在后面再补一个 `字典类型`
  成 `标签:字段名:字典类型`（选择器里自动把 0/1 显示成字典标签）；**不配就只显示名称列**
- **搜索**：平铺目标走**后端分页 + 关键字**（关键字发到 `labelField` 那个查询列上 ——
  所以目标表那个列得是可查询列）；**树形目标没法分页**（分页的树没意义）→ 一次拉全量、本地过滤，
  表格用 `el-table` 的树形模式，层级不丢
- 回显：拿到 id 后走**详情接口**（`{列表地址}/{id}`）反查名称，所以列表页不用另配什么
- 组件在 `frontend/src/components/TableSelect/`，**全局注册**（`main.ts`），生成物直接写 `<table-select>`

> 选项来自接口的字段（`optionsApi`）若也想用选择器，**显式配 `pickerColumns`** 即可；
> 小枚举留着直接用下拉更好。

> ⚠️ **列表里默认显示的是 ID，不是名称**（演示产品的「所属分类」列就是裸的 `categoryId`）。
> 想显示名称，用下面的「冗余显示列」。

### 冗余显示列：让列表 / 导出显示名称

在关联字段的规则里多配几个键，让它在**本表**另存一份名称：

```json
{"treeApi":"/biz/demoCategory/list","valueField":"categoryId","labelField":"categoryName",
 "parentField":"parentId",
 "displayColumn":"categoryName",      // 本表存名称的列（写 javaField）
 "refTable":"biz_demo_category",      // 关联表
 "refValueColumn":"category_id",      // 关联表的取值列（数据库列名）
 "refLabelColumn":"category_name"}    // 关联表的名称列（数据库列名）
```

- 主表另建一个**普通列**存名称（如 `category_name varchar(128)`）：`input`、**不勾表单**、
  `list` / `query` 按需勾 —— 勾了 `query` 就能**按名称模糊搜**，导出也自然是名称
- `valueField` / `labelField` 是**接口返回的 JSON 键**（前端反查名称用）；
  `refValueColumn` / `refLabelColumn` 是**数据库列名**（后端算名称用）—— **不是一回事，别混**
- 谁写：**前端提交时写一遍，后端保存时用 SQL 子查询再算一遍**。
  后端那条是权威 —— 手写 API 调用、导数据也能对上；前端那条只为提交后的即时状态
- 多值关联（`checkbox` / 多选 `select`）：名称用逗号拼一份，后端走 `group_concat` + `find_in_set`
- 列表里**只显示名称列**，裸 ID 列不再渲染

> ⚠️ **名称是冗余的，会陈旧** —— 关联表改了名，本表要等下次保存才更新。批量修用一条 SQL（单值）：
>
> ```sql
> update biz_demo_product p join biz_demo_category c on c.category_id = p.category_id
>   set p.category_name = c.category_name where p.category_id is not null;
> ```

> ⚠️ 只对 **`treeselect` 与选项来自接口/写死的字段**生效。字典列不需要 ——
> 列表里的 `dict-tag` 本来就会把码值翻成标签。

## 3. 一对多（主子表）

配置：主表编辑页 → 生成模板选**主子表**，再选「关联子表的表名」与「子表关联的外键名」。
子表是**独立导入**的一张表，列配置也在它自己身上。

产物：主表列表照旧；**明细在新增/修改弹窗里**内联编辑 —— 子表没有独立页面，也没有自己的菜单权限。

> ⚠️ 只有一层，子表不能再挂子表。
>
> **删主记录时的连带**：明细跟着主表的删除类型走 —— 物理删就把明细一起清掉；
> 勾了「逻辑删除」（见 `模板增强清单.md`）则**都不动**，取消删除时明细一起回来。

## 4. 多对多

两种做法，按需要选：

| 做法 | 什么时候够用 | 代价 |
|---|---|---|
| **逗号串字段**（`checkbox` / 多选 `select`、`treeselect`） | 「标签、场景」这种只存不解、不反查的 | 没法从关联表那头反查 |
| **辅助表**（下面这套） | 要真关联、要从关联表反查 | 多一张表 |

### 辅助表怎么做

关联关系存在**辅助表**里，主表没有那一列。配置挂在**显示列**上：

```json
{"junctionTable":"biz_demo_product_tag",   // 辅助表（中间表）
 "junctionMainFk":"product_id",            // 它指向**本表**的外键
 "junctionRefFk":"tag_id",                 // 它指向**关联表**的外键
 "idsField":"tagIds",                      // 实体上的瞬时字段（库里没有这一列）
 "optionsApi":"/biz/demoTag/list","optionLabel":"tagName","optionValue":"tagId",
 "displayColumn":"tagNames",               // 名称存本表哪一列
 "refTable":"biz_demo_tag","refValueColumn":"tag_id","refLabelColumn":"tag_name"}
```

生成出来的东西：

- 表单里是一个**多选**，绑 `form.tagIds`（瞬时字段），选项来自 `optionsApi`
- 保存时 Service **先删后插**辅助表，再按辅助表把显示列重算一遍 —— 同一个事务，一条不多一条不少
- 查详情时把辅助表里的 id 集合带出来回显；**删主记录时一并清掉关联**（不留孤儿行）
- 列表 / 导出吃显示列（名称，逗号分隔）

> **删主记录时的连带**：同样跟着主表的删除类型走 —— 物理删就把辅助表里的关联一起清掉；
> 勾了「逻辑删除」则**都不动**（关联跟着主记录一起「软挂」）。

样板：`biz_demo_tag` + `biz_demo_product_tag` + 产品表的 `tag_names`，
建表脚本见 `backend/sql/biz_demo_tag.sql`。

> ⚠️ 显示列**不要**配成可编辑字段（`is_insert=0`）—— 它的值由后端重算，手填的会被覆盖。

## 5. 自身父子关联（树表）

配置：生成模板选**树表**，再选三列 —— **树编码**（`treeCode`，主键）、
**树父编码**（`treeParentCode`）、**树名称**（`treeName`，显示用）。

表结构：`parent_id`，需要按层级查子孙就再加 `ancestors`。

> ⚠️ 两个坑（详见 `docs/业务/演示产品分类.md` 与 `模板增强清单.md`）：
> **树名列必须排在第一列**（`el-table` 的树形缩进固定作用在第一列）；
> **`ancestors` 生成器不维护** —— 移动节点要自己更新它。

## 6. 枚举别建关联表

「状态、类型、等级」这类固定枚举用**字典**，不要为它建一张表再关联：
稳定枚举建 `sys_dict_type`，一次性小枚举写 `validation_rule.options`，会变的数据用 `optionsApi`。
三种来源与优先级见 `校验规则.md` §2。

## 还有哪些情况

| 形态 | 支持 | 怎么办 |
|---|---|---|
| 逻辑删除（`del_flag`） | 惯例 | ⚠️ 别和唯一索引一起用：软删过的行仍占着 `code`，再建同名记录会撞唯一键 |
| 多级明细（孙表） | ❌ | 拆成两套主子表（各自一份菜单），或手写 |
| 联合主键 / 无主键 | ❌ | 加一个自增单主键列 |
| 按部门的数据权限 | 框架层有 | `@DataScope`，但**生成物没挂**（只在 `system` 的手写 Service 里用）—— 要按部门过滤得自己在 Service 上加 |
| 关联对象在别的服务/库 | 只读可以 | `treeselect` 指向那个服务的 list 接口 |
| 一个字段关联多张表 | ❌ | 一个字段只对应一个数据源，要两个就建两个字段 |
| 图片 / 附件 | ✅ | 见 `字段类型.md`（单图配 `{"limit":1}`） |
